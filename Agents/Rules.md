# Rules

## Git 및 작업 범위

- 사용자가 명시적으로 요청하지 않은 Git 커밋·푸시·히스토리 변경을 금지한다. `git add`, `git commit`, `git push`, `git reset`, `git rebase`, `git cherry-pick`, `git clean`은 자동 완료 절차가 아니다. 상태 조회와 Diff 분석으로 변경 사항을 확인한다.
- `reset --hard`, 강제 push, 사용자 변경 삭제를 금지한다. 자동 커밋을 취소하는 새 커밋도 자동 생성하지 않는다.
- 복구 전 브랜치·HEAD·최근 커밋·작업 트리·스테이징을 확인한다. 작성자 이름만으로 주체를 단정하지 않고 대화·실제 변경과 대조한다. 대상을 식별하지 못하거나 사용자 변경과 충돌하면 중단하고 방안을 보고한다.
- 게임 기능·기획, Unity 버전·패키지는 요청 범위 밖에서 변경하지 않는다. 기존 변경과 다른 에이전트 작업을 보존한다.
- 요청을 수행하는 데 필요한 자료 읽기·허용된 범위의 파일 수정·작업 기록만 진행한다. 편의를 위한 별도 후속 작업을 스스로 추가하지 않는다.
- 구현 요청만으로 배포·설치·커밋·푸시·병합을 실행하지 않는다. 다만 구현에 필요한 컴파일 확인은 허용하며, 필요성이 명확한 경우에만 빌드할 수 있다. 기능 테스트는 별도의 명시적 요청·승인을 필요로 한다. 상세 범위는 아래 검증 규칙에 따른다.
- 핵심은 요청 범위를 지키는 운영 규칙이다. 별도 기술적 차단 도구의 구축을 미해결 과제로 두거나 임의로 도입하지 않는다.

## 개발 코드 규칙

### 설계 품질

- 객체지향 설계를 기반으로 확장성과 유지보수성을 우선한다. 책임과 경계를 분명히 하되, 추상화·클래스·파일을 필요 이상으로 늘리지 않는다.
- 연관된 스크립트는 기능이나 시스템 단위 폴더로 함께 관리한다. 폴더·계층·패턴을 일괄 생성하지 않으며 게임 아키텍처는 확정된 설계 문서를 따른다.
- 단순한 구조와 중복 감소 중 어느 한쪽을 기계적으로 고집하지 않는다. 가독성과 간결성을 지키기 어려운 경우 문제와 선택지를 설명하고 사용자 판단을 요청한다.
- 사용자가 제공한 게임 기획과 기존 개발 규칙을 구현 전에 대조한다. 충돌하지 않는 기술적 세부사항은 독자적으로 판단하되, 기획이나 확정 규칙을 변경하는 판단은 승인받는다.

### 명명·주석·설정값

- 변수·함수·클래스 이름은 역할이 드러나는 직관적이고 단순한 단어 조합을 사용한다. 불필요한 약어, 난해한 용어, 과도하게 긴 이름을 피한다. 기존 코드와 함께 사용할 때는 일관성을 유지한다.
- 함수 선언 바로 위에 함수의 역할을 설명하는 한 줄 `// Role: ...` 주석을 작성한다. 매개변수 설명이 꼭 필요할 때에만 별도의 `// Parameter: ...` 주석을 추가한다.
- 함수 내부 인라인 주석은 동작 이해에 반드시 필요한 핵심 로직에만 사용한다. 코드가 스스로 설명하는 내용을 반복하지 않는다.
- 인스펙터에서 조정하는 주요 게임 시스템 변수에는 Unity `[Tooltip("...")]`을 사용해 변수의 의미나 조정 효과를 간략하고 명확하게 설명한다. 관련 없는 모든 필드에 일률적으로 추가하지 않는다.

### 변경 권한

- 단일 구조 내부에서 기능과 외부 계약을 유지하는 소규모 리팩터링은 독자적으로 수행할 수 있다.
- 여러 시스템·계층·공용 인터페이스에 영향을 주는 대규모 리팩터링은 변경 목적, 대상, 예상 영향과 대안을 보고하고 승인받은 뒤 수행한다.
- 사용자가 파일 생성·삭제를 직접 지시하지 않은 경우, 새 파일·폴더 생성이나 기존 파일 삭제가 필요하면 대상과 사유를 먼저 설명하고 승인받는다. 기존 파일의 허용된 범위 내 수정과 기존 Queue/State의 규정된 기록 갱신은 여기에 해당하지 않는다.
- 파일 이동·이름 변경이 참조·공용 API·다른 구조에 영향을 주면 대규모 변경과 같이 취급한다. 에셋 이동·삭제 시에는 Unity 참조 보존 규칙도 따른다.
- 판단의 영향 범위가 불분명하거나 위험이 크면 임의로 진행하지 않고 판단에 필요한 사실을 보고한다.

### 패키지·외부 의존성

- 새 패키지 또는 외부 라이브러리를 도입하거나 기존 의존성을 변경하기 전 사용자 승인을 받는다.
- 승인 요청에는 패키지명·출처, 용도, 도입 전후의 차이, 예상 장점, 주의사항(호환성·유지관리·추가 의존성 등)을 간략하게 제시한다.
- Unity 공식 지원 패키지 또는 널리 사용되고 안정성이 확인된 패키지·오픈소스를 우선 검토한다. 인지도가 낮거나 검증 근거가 부족한 패키지는 가능한 한 피한다.
- 설치·버전 변경·잠금 파일 수정은 승인 전 수행하지 않는다. 이미 있는 도구와 기능을 먼저 검토해 중복 도입을 피한다.

## 개발 워크플로

### 시스템 골격 우선 개발

1. RoadMap에서 시스템별 구현 목표와 관련 기능을 묶고, 의존성을 고려해 작업 순서를 정한다. 확정되지 않은 기획 내용을 임의로 채우지 않는다.
2. 시스템 작업을 시작하기 전에 목적, 첫 번째 대표 기능, 예상 수정 범위, 관련 의존성, 검증 계획, 알려진 위험을 간략히 보고한다. 일반적인 계획 보고는 구현 승인 절차가 아니다.
3. 각 시스템에서 실제로 동작할 수 있는 대표 기능 하나만 먼저 구현한다. 미리 여러 변형·타입·콘텐츠를 대량 구현하지 않는다.
4. 필요한 컴파일 오류를 확인하고 조치한다. 기능 테스트는 목적·대상·성공 조건을 설명해 사용자에게 명시적으로 요청한다. 승인되지 않은 기능 테스트는 실행하지 않는다.
5. 사용자 테스트 또는 승인된 테스트에서 정상 동작이 확인되면 다음 시스템의 대표 기능을 같은 방식으로 진행한다. 검증하지 못한 시스템을 검증 완료로 취급하지 않으며 다음 단계로 임의 진입하지 않는다.
6. 전체 시스템의 기본 골격이 준비된 후 각 시스템의 추가 기능·타입·콘텐츠를 순차적으로 확장한다.

### 계획 보고와 승인 판단

- 구현 계획은 사용자가 작업 방향을 인지하기 위한 사전 보고이다. 기획과 규칙에 부합하고 별도 승인 항목이 없는 경우 구현을 계속한다.
- 게임 기획의 변경, 확정 규칙·설계와의 충돌, 영향이 큰 기술적 선택, 여러 구조에 걸친 대규모 변경은 충돌·영향·선택지를 보고한 뒤 사용자 승인을 요청한다.
- 사전 계획에 포함되지 않은 승인 대상이 구현 도중 발견되면 해당 부분을 멈추고 사용자 판단을 요청한다. 안전하게 분리 가능한 다른 허용 작업만 진행할 수 있다.
- 사용자에게 판단을 요청할 때는 확인된 사실, 판단이 필요한 이유, 선택 가능한 대안을 구분한다. 승인되지 않은 결정을 완료된 설계로 문서화하지 않는다.

### 브랜치·커밋·통합

- `main`은 여러 시스템의 검증·통합이 끝난 최종 결과를 관리한다. 다른 시스템 개발로 전환하거나 RoadMap의 이전 작업과 성격이 다른 시스템을 시작할 때는 해당 시스템용 브랜치를 제안한다.
- 새 브랜치 생성·전환은 이름·목적·기준 브랜치와 현재 변경의 처리 방안을 설명하고 사용자 승인 후 진행한다. 기존 미커밋 변경을 임의로 이동하거나 덮어쓰지 않는다.
- 시스템 구현 중에는 승인된 해당 작업 브랜치에서 변경한다. `main`으로의 병합·통합도 사용자 지시 없이 진행하지 않는다.
- 커밋과 푸시는 원칙적으로 하나의 완료·공유 단위로 취급한다. 사용자의 명시적 커밋 지시가 있을 때 승인 범위를 확인한 뒤 수행하며, 사용자가 커밋만 요청하거나 푸시를 제외했다면 그 지시를 우선한다.
- 커밋이나 푸시를 먼저 제안할 수 있는 경우는 브랜치 운영·작업 인계에 필요하거나 실질적으로 작업 안전을 위해 필요한 때로 제한한다. 제안 자체는 실행 허가가 아니다.
- 커밋 후 푸시가 실패하면 성공한 단계와 실패한 단계를 구분해 보고하고, 히스토리 수정·강제 푸시로 임의 복구하지 않는다.

### 완료 보고

- 변경한 파일과 구현한 기능은 간략하게 보고한다.
- 컴파일·빌드·기능 테스트 등 검증 결과는 실시 여부, 범위, 성공·실패, 미확인 사항으로 구분해 보고한다.
- 발견된 문제는 재현 조건, 원인 또는 미확인 원인, 영향, 조치 내용과 필요한 결정을 상세히 보고한다.
- 후속 작업과 중단 조건이 있으면 State에 반영한다. Queue에는 다음 에이전트가 정확히 재개하는 데 필요한 기록만 남긴다.

## Unity CLI·MCP

- C# 검색·수정과 Git 확인은 일반 파일·CLI 도구를 사용한다.
- Scene, Prefab, Component, ScriptableObject 및 직렬화 참조 조회·수정은 Unity CLI를 우선하고, 직접 호출이 불가능하거나 MCP가 더 적합하면 MCP를 사용한다.
- 기존 Unity Pipeline·CLI·MCP 구성을 먼저 확인하고 재사용한다. 동일 기능을 중복 설치하거나 자체 실행 파이프라인을 만들지 않는다.
- Editor 작업 시작 시 연결 상태와 대상 프로젝트 경로를 확인한다. 현재 저장소를 대상으로 하며 참고 프로젝트의 Editor를 대신 조작하지 않는다. 연결 오류나 Editor 재시작이 없으면 같은 확인을 반복하지 않는다.
- 이미 연결된 MCP 서버를 수동으로 중복 실행하지 않는다. 실패 시 대상 경로, 컴파일 오류, Safe Mode, 연결 정보를 먼저 확인한다. 원인 확인 없이 재시작·재설치·설정 변경을 반복하지 않는다.
- 에셋과 `.meta`, GUID, 직렬화 참조를 함께 보존한다. 가능하면 Unity API를 사용하고 직접 파일 수정 시 참조 무결성을 확인한다.
- 사용자 작업 중인 Scene을 임의 저장하거나 닫지 않는다. 테스트를 이유로 사용자 변경을 덮어쓰지 않는다.
- Unity 버전 및 패키지는 명시적 요청·승인 없이 변경하지 않는다. 도구 미설치·연결 정보 부족 시 가능한 범위를 보고한다.

## 컴파일·빌드·테스트·검증

- 구현과 직접 관련된 컴파일 오류 확인은 명시적 요청 없이 수행할 수 있다. 이미 Editor의 컴파일 결과를 확인할 수 있다면 동일 목적의 중복 실행을 피한다.
- 빌드도 명시적 요청 없이 실행할 수 있으나, 단순 컴파일 확인이나 사용자가 Editor에서 확인할 수 있는 사항을 위해 반복적으로 수행하지 않는다. 빌드가 실제로 필요한 상황인지 먼저 판단한다.
- **기능 테스트(Edit Mode·Play Mode·수동 동작 확인 등)는 목적과 범위, 성공 기준을 설명해 사용자에게 명시적으로 요청하고, 승인 또는 테스트 수행 지시를 받은 후에만 실행한다.** 단순 컴파일 확인을 테스트 승인으로 해석하지 않는다.
- 작업 지시에 검증 범위가 명시되어 승인된 경우, 그 범위 내 검증은 자율적으로 수행할 수 있다. 승인 범위를 벗어난 다른 테스트·검증으로 확대하지 않는다.
- 사용자가 직접 Unity Editor로 테스트할 경우 대상 시나리오와 기대 결과를 전달한다. 결과를 전달받기 전에는 테스트 통과로 기록하지 않는다.
- 검증 시 관련 기존 테스트를 우선 검토하고, 대상·성공 조건·필요 시 시간 상한을 정한다. 컴파일 성공·빌드 성공·기능 동작 확인은 별도 결과로 구분한다.
- 요청·허용 범위 밖의 전체 테스트·장시간 성능 테스트·전체 재임포트·Library 삭제를 추가하지 않는다. 성공한 검증을 이유 없이 반복하지 않는다.
- 실행하지 않은 항목은 미실행 또는 확인 대기로 보고한다. 기존 결과를 새 실행 결과처럼 표현하지 않는다. 오류는 관련 로그 중심으로 보고한다. Editor가 없거나 연결되지 않았다면 실행 제한을 알린다.

## 기록과 복구

- Queue 열람은 매 작업·새 세션의 필수 절차가 아니다. 사용자가 이전 작업을 이어서 진행하도록 요청하거나, 다른 에이전트의 작업을 인계받거나, 진행 기록 확인을 요청하는 등 실행 맥락이 필요할 때 관련 부분만 읽는다. 더 오래된 근거가 필요할 때만 History를 조회한다. 기록 작성과 필요 시 열람은 별개의 규칙이다.
- Queue는 작업 목록이 아닌 최근 실행 맥락 FIFO다. `Queue.md`의 `queue_limit`을 양의 정수 N으로 설정한다(기본 100). History는 제한하지 않는다.
- 사용자 요청 메시지와 그 요청에 대한 설명·명령·출력·오류·파일 변경·최종 결과를 하나의 작업 기록 세트로 묶는다. 같은 작업 ID를 사용하고 요청 원문 아래에 진행 과정과 결과를 이어서 저장한다. 결과를 요청과 분리한 독립 기록으로 남기지 않는다. 중단 상태도 같은 세트에 유지한다.
- Queue에서 History로 이관할 때도 요청과 결과를 분리하지 않고 작업 기록 세트 전체를 함께 옮긴다. 세트 경계를 보존하기 위해 오래된 세트 전체를 이관할 수 있다.
- 이벤트는 고유 ID, 기록 시간(시간대 포함), 종류, 연관 작업 ID, 실제 원문 입력·명령·핵심 출력 및 상태를 포함한다. 여러 줄 원문은 JSON 문자열 또는 들여쓰기 블록으로 보존한다.
- 사용자 요청 원문과 실제 실행 명령·도구 인자, 결과·오류의 핵심 원문, 변경 파일, 중단·복구 과정을 순서대로 기록한다. 다른 에이전트가 정확히 판단하는 데 필요한 커밋·브랜치·경로·검증 상태·미해결 조건을 명시한다.
- 기록은 간략하게 유지하되 원문을 왜곡하거나 핵심 결과를 누락하지 않는다. 긴 반복 정상 출력은 중복을 줄일 수 있지만 생략 여부와 범위를 표시한다. 전체를 보존하지 않은 경우 원문 전체를 기록했다고 주장하지 않는다. 누락은 누락으로, 소급 요약은 요약으로 표시한다. 숨겨진 추론은 기록 대상이 아니다.
- 명령 전에 `started`를 저장하고 종료 후 같은 작업 ID로 `completed` 및 실제 종료 코드·핵심 결과를 추가한다. 중단·결과 불명은 `interrupted` 또는 `unknown`으로 남긴다. 기록기 자신의 파일 입출력은 재귀 기록하지 않는다.
- 작업 중 설명, 실행 명령·도구, 결과·출력·오류, 수정·중단·재개 과정을 필요한 만큼 기록한다. 완료 요약만으로 작업 과정과 근거를 대체하지 않는다.
- 에이전트가 작업하면서 Queue를 갱신한다. 별도 자동 수집 플랫폼을 구축하지 않는다. 실제로 접근·기록한 내용과 누락을 구분한다.
- N을 초과하면 가장 오래된 작업 기록 세트의 이벤트를 원문·ID 그대로 History 끝에 먼저 복사하고 확인한 뒤 Queue에서 제거한다. 이관 중단 시 두 파일의 동일 ID·내용을 비교해 중복만 제거한다. 같은 ID의 내용이 다르면 덮어쓰지 않고 중단한다. 이미 기록된 원문을 이관 과정에서 요약으로 대체하지 않는다.
- 중요한 결정·진행 상태·미해결 문제·다음 행동은 State에 갱신한다. 미완료 작업은 Queue에서 밀려나도 State에 유지하고 History의 ID를 참조한다.
- 새 세션은 AGENTS의 순서대로 복구한다. 결과 불명 시 실제 프로세스·파일·Git·외부 결과를 먼저 확인하고 근거를 남긴다. 완료 신호가 없다는 이유로 명령을 재실행하지 않는다.
- 비밀·인증정보는 기록·전송하지 않는다. 마스킹은 표시하고 원문 전체를 보존했다고 주장하지 않는다.

## 최신 커밋 기준 인계

- 서로 다른 기기는 저장소의 최신 커밋을 기준으로 작업한다. 해당 커밋에 포함된 State와 실제 파일을 확인하고, 작업 인계에 필요한 실행 맥락이 있으면 Queue의 관련 부분을 읽는다. History는 더 오래된 근거가 필요할 때 조회한다.
- 커밋하지 않은 기록을 기기 간 동기화할 필요는 없다. 외부 공유 서비스·수동 파일 전달 절차를 별도로 도입하지 않는다.
- 커밋·푸시는 사용자의 명시적 지시가 있을 때만 수행한다. 인계 필요성을 자동 커밋의 허가로 해석하지 않는다.
- 시작 시 현재 커밋과 기존 변경을 확인한다. 최신 여부를 확인할 수 없으면 미확인으로 알리며, 사용자 변경을 덮어쓰거나 임의로 pull·merge하지 않는다.

## 문서 역할과 근거

GameDesign은 기획, RoadMap은 개발 단계, Architecture는 현재 기술 구조와 확정 설계, Rules는 운영·개발 규칙과 워크플로, State는 진행 상태, Queue/History는 실행 기록을 담당한다. 원문 로그나 임시 시도를 설계 문서에 중복 저장하지 않는다.

Unity 운영 기준은 로컬 `D:/Mini-Civilization/AGENTS.md`에서 확인했다([참고 저장소](https://github.com/K-Jung-H/Mini-Civilization)). 해당 프로젝트의 기획·버전·패키지 설정은 복사하지 않는다.

[Codex rules](https://developers.openai.com/codex/rules)는 샌드박스 밖 명령의 승인 정책이며 모든 실행을 차단하는 기능은 아니다. [CLI JSON 이벤트](https://developers.openai.com/codex/noninteractive)는 해당 CLI 실행의 이벤트이며 데스크톱 대화를 자동으로 연결하지 않는다.
