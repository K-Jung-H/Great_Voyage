# Rules

## Git 및 작업 범위

- 사용자가 명시적으로 요청하지 않은 Git 커밋·푸시·히스토리 변경을 금지한다. `git add`, `git commit`, `git push`, `git reset`, `git rebase`, `git cherry-pick`, `git clean`은 자동 완료 절차가 아니다. 상태 조회와 Diff 분석으로 변경 사항만 보고한다.
- reset --hard, 강제 push, 사용자 변경 삭제를 금지한다. 자동 커밋을 취소하는 새 커밋도 자동 생성하지 않는다.
- 복구 전 브랜치·HEAD·최근 커밋·작업 트리·스테이징을 확인한다. 작성자 이름만으로 주체를 단정하지 않고 대화·실제 변경과 대조한다. 대상을 식별하지 못하거나 사용자 변경과 충돌하면 중단하고 방안을 보고한다.
- 게임 기능·기획, Unity 버전·패키지는 요청 범위 밖에서 변경하지 않는다. 기존 변경과 다른 에이전트 작업을 보존한다.
- 요청을 수행하는 데 필요한 자료 읽기·파일 수정·과정 기록은 해당 작업 범위에서 진행한다. 편의를 위한 별도 후속 작업을 스스로 추가하지 않는다.
- 구현 요청은 테스트·컴파일·빌드·배포·설치·커밋·푸시 요청을 포함하지 않는다. 명시적으로 요청된 후속 작업만 수행한다. 필요성을 발견하면 이유와 미실행 사실을 보고하고 요청을 기다린다.
- 핵심은 요청 범위를 지키는 운영 규칙이다. 별도 기술적 차단 도구의 구축을 미해결 과제로 두거나 임의로 도입하지 않는다.

## Unity CLI·MCP

- C# 검색·수정과 Git 확인은 일반 파일·CLI 도구를 사용한다.
- Scene, Prefab, Component, ScriptableObject 및 직렬화 참조 조회·수정은 Unity CLI를 우선하고, 직접 호출이 불가능하거나 MCP가 더 적합하면 MCP를 사용한다.
- 기존 Unity Pipeline·CLI·MCP 구성을 먼저 확인하고 재사용한다. 동일 기능을 중복 설치하거나 자체 실행 파이프라인을 만들지 않는다.
- Editor 작업 시작 시 연결 상태와 대상 프로젝트 경로를 확인한다. 현재 저장소를 대상으로 하며 참고 프로젝트의 Editor를 대신 조작하지 않는다. 연결 오류나 Editor 재시작이 없으면 같은 확인을 반복하지 않는다.
- 이미 연결된 MCP 서버를 수동으로 중복 실행하지 않는다. 실패 시 대상 경로, 컴파일 오류, Safe Mode, 연결 정보를 먼저 확인한다. 원인 확인 없이 재시작·재설치·설정 변경을 반복하지 않는다.
- 에셋과 .meta, GUID, 직렬화 참조를 함께 보존한다. 가능하면 Unity API를 사용하고 직접 파일 수정 시 참조 무결성을 확인한다.
- 사용자 작업 중인 Scene을 임의 저장하거나 닫지 않는다. 테스트를 이유로 사용자 변경을 덮어쓰지 않는다.
- Unity 버전 및 패키지는 명시적 요청 없이 변경하지 않는다. 도구 미설치·연결 정보 부족 시 가능한 범위를 보고한다.

## 테스트·검증 실행 범위

- 사용자가 테스트 또는 검증 실행을 명시적으로 요청한 경우에만 해당 범위에서 수행한다. 구현 완료를 이유로 컴파일·테스트·빌드를 자동 실행하지 않는다.
- 실행하지 않은 항목은 미실행으로 보고한다. 기존 결과를 새 실행 결과처럼 표현하지 않는다.
- 검증이 요청되면 관련 기존 Edit Mode·Play Mode 테스트를 우선하고, 대상·성공 조건·시간 상한을 정한다. 컴파일 성공과 기능 검증 성공을 구분한다.
- 요청 범위 밖의 전체 테스트·장시간 성능 테스트·전체 재임포트·Library 삭제를 추가하지 않는다. 성공한 검증을 이유 없이 반복하지 않는다.
- 정상 결과는 간략히, 오류는 관련 로그 중심으로 기록한다. Editor가 없거나 연결되지 않았다면 해당 실행 제한을 보고한다.

## 기록과 복구

- Queue 열람은 매 작업·새 세션의 필수 절차가 아니다. 사용자가 이전 작업을 이어서 진행하도록 요청하거나, 다른 에이전트의 작업을 인계받거나, 진행 기록 확인을 요청하는 등 실행 맥락이 필요할 때 관련 부분만 읽는다. 더 오래된 근거가 필요할 때만 History를 조회한다. 기록 작성과 필요 시 열람은 별개의 규칙이다.
- Queue는 작업 목록이 아닌 최근 실행 맥락 FIFO다. Queue.md의 queue_limit을 양의 정수 N으로 설정한다(기본 100). History는 제한하지 않는다.
- 이벤트는 고유 ID, 기록 시간(시간대 포함), 종류, 연관 작업 ID, 원문 입력·출력, 상태를 포함한다. 여러 줄 원문은 JSON 문자열 또는 들여쓰기 블록으로 보존한다.
- 사용자·에이전트 대화 원문, 도구 호출·명령, 결과·오류, 파일 변경, 중단·복구를 발생 순서로 기록한다. 누락은 누락으로, 소급 요약은 요약으로 표시한다. 숨겨진 추론은 대상이 아니다.
- 명령 전에 started를 저장하고, 종료 후 같은 작업 ID로 completed 및 실제 종료 코드·결과를 추가한다. 중단·결과 불명은 interrupted 또는 unknown으로 남긴다. 기록기 자신의 파일 입출력은 재귀 기록하지 않는다.
- 사용자가 제시한 예시처럼 작업 중 설명, 실제 실행한 명령·도구, 결과·출력·오류, 수정·중단·재개 과정을 기록한다. 완료 요약만으로 실행 과정을 대체하지 않는다.
- 에이전트가 작업하면서 Queue를 갱신한다. 별도 자동 수집 플랫폼 구축이 목적이 아니다. 실제로 접근·기록한 내용과 누락을 구분한다.
- N을 초과하면 가장 오래된 이벤트를 원문·ID 그대로 History 끝에 먼저 복사하고 확인한 뒤 Queue에서 제거한다. 이관 중단 시 두 파일의 동일 ID·내용을 비교해 중복만 제거한다. 같은 ID의 내용이 다르면 덮어쓰지 않고 중단한다. 원문을 요약으로 대체하지 않는다.
- 중요한 결정·진행 상태·미해결 문제·다음 행동은 State에 갱신한다. 미완료 작업은 Queue에서 밀려나도 State에 유지하고 History의 ID를 참조한다.
- 새 세션은 AGENTS의 순서대로 복구한다. 결과 불명 시 실제 프로세스·파일·Git·외부 결과를 먼저 확인하고 근거를 남긴다. 완료 신호가 없다는 이유로 명령을 재실행하지 않는다.
- 비밀·인증정보는 기록·전송하지 않는다. 마스킹은 표시하고 원문 전체를 보존했다고 주장하지 않는다.

## 최신 커밋 기준 인계

- 서로 다른 기기는 저장소의 최신 커밋을 기준으로 작업한다. 해당 커밋에 포함된 State와 실제 파일을 확인하고, 작업 인계에 필요한 실행 맥락이 있으면 Queue의 관련 부분을 읽는다. History는 더 오래된 근거가 필요할 때 조회한다.
- 커밋하지 않은 기록을 기기 간 동기화할 필요는 없다. 외부 공유 서비스·수동 파일 전달 절차를 별도로 도입하지 않는다.
- 커밋·푸시는 사용자가 명시적으로 요청했을 때만 수행한다. 인계 필요성을 자동 커밋의 허가로 해석하지 않는다.
- 시작 시 현재 커밋과 기존 변경을 확인한다. 최신 여부를 확인할 수 없으면 미확인으로 알리며, 사용자 변경을 덮어쓰거나 임의로 pull·merge하지 않는다.

## 문서 역할과 근거

GameDesign은 기획, RoadMap은 개발 단계, Architecture는 현재 기술 구조와 확정 설계, State는 진행 상태, Queue/History는 실행 기록을 담당한다. 원문 로그나 임시 시도를 설계 문서에 중복 저장하지 않는다.

Unity 운영 기준은 로컬 D:/Mini-Civilization/AGENTS.md에서 확인했다([참고 저장소](https://github.com/K-Jung-H/Mini-Civilization)). 해당 프로젝트의 기획·버전·패키지 설정은 복사하지 않는다.

[Codex rules](https://developers.openai.com/codex/rules)는 샌드박스 밖 명령의 승인 정책이며 모든 실행을 차단하는 기능은 아니다. [CLI JSON 이벤트](https://developers.openai.com/codex/noninteractive)는 해당 CLI 실행의 이벤트이며 데스크톱 대화를 자동으로 연결하지 않는다.
