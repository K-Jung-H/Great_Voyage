# Rules — 운영·개발 규칙

## 1. 적용 범위와 판단 순서

- 사용자 최신 명시 지시, 실제 Git·프로젝트의 존재 사실, AGENTS/Rules의 절차, GameDesign의 게임 요구사항, ArchitectureStandards의 신규 구현 구조, RoadMap의 순서, Architecture/State/Queue/History의 기존 기록을 함께 확인한다. 기획 및 기술 구조는 서로 다른 역할의 기준이므로 충돌 발견 시 보고한다.
- `ArchitectureStandards.md`의 Scene/UI/통합 기준은 신규 및 재구성 작업에 필수다. `Architecture.md`에 남은 과거 프로토타입 방식은 구현 이력이지 앞으로 따라야 할 규범이 아니다.
- 요청하지 않은 기능 추가, 기획 변경, 패키지 변경, UI 도안 임의 변경, 최종 게임 규칙 변경을 금지한다.

## 2. Git·권한·변경 보존

- 시작 전 브랜치·HEAD·작업 트리·스테이징·최근 변경을 확인해 기존 작업을 보호한다. 결과가 불명확한 명령을 확인 없이 재실행하지 않는다.
- 사용자 명시 지시 없이 `git add`, `commit`, `push`, `reset`, `rebase`, `cherry-pick`, `clean`, `merge`로 저장소 상태·히스토리를 변경하지 않는다. 강제 push, `reset --hard`, 사용자 데이터 삭제는 금지한다.
- 구현 요청은 파일 생성·삭제·패키지 설치·대규모 리팩터링·커밋·푸시·병합의 포괄 승인이 아니다. 신규 파일·폴더가 필요할 때는 대상·역할을 사전 제시하고 승인을 확인한다.
- 신규 시스템 브랜치는 이름·목적·기준점·미커밋 변경 처리안을 제시해 승인받는다. `main` 통합은 별도 사용자 지시를 받는다.
- 복원 불가능한 편집, 여러 시스템의 공용 계약 변경, Scene 구조 전면 개편, 자산 대량 이동·삭제는 변경 대상·영향·저장 호환성·대안을 설명하고 사전 승인받는다.
- 이미 승인된 변경 범위 내의 일반적인 로직 편집·컴파일 확인·문서 기록은 불필요하게 재승인을 요구하지 않는다.
- 승인은 사용자가 명시한 대상·목적·범위에 적용한다. 구체 파일 생성·구조 변경·테스트를 이미 지시하거나 승인했다면 같은 범위의 승인을 반복하지 않는다. 기술 세부사항의 자율 결정은 승인 대상 작업의 포괄 허가가 아니며, 범위를 벗어난 승인 대상만 추가로 확인한다.

## 3. 개발 품질과 코드

- 객체지향 설계와 명확한 책임 경계를 우선한다. 불필요한 추상화·인터페이스·매니저·파일은 만들지 않는다. 단일 클래스에 무관한 규칙·UI·상태 관리가 누적되면 책임을 검토한다.
- 관련 코드는 도메인 또는 기능 단위로 관리하며 이름은 역할이 명확해야 한다. 수치·설정은 필요한 수준에서 Inspector/정의 데이터로 조정 가능하게 한다. 주요 Inspector 변수에 간결한 `[Tooltip]`을 사용한다.
- 함수 설명이 필요한 경우 바로 위에 `// Role: ...`, 매개변수 설명은 필요한 때만 `// Parameter: ...`를 사용한다. 구현 본문 내 불필요한 설명 주석은 넣지 않는다.
- 기획에서 정한 UI 구도·씬 연결·공간 배치는 단순 장식이 아니라 구현 요구사항이다. 임시 이미지는 허용하되 기능 테스트 편의를 이유로 구조를 제거하지 않는다.
- 상태(저장 원본), 정의 데이터, 규칙 서비스, Scene/Prefab의 표현, UI Controller, 시작·전환 흐름을 구분한다. 데이터와 규칙의 동일 원본을 여러 개발 씬에 복제하지 않는다.
- 화면의 기본 UI 트리는 Editor에서 Scene/Prefab으로 배치한다. Controller는 직렬화 참조로 제어한다. 코드의 `new GameObject`/`RectTransform` 생성으로 완전한 화면·기본 레이아웃을 조립하지 않는다. 동적 목록 아이템은 사전 제작 Prefab 인스턴스화만 허용한다.
- 신규 Scene은 역할·생명주기·루트·의존성·저장/복원 정책이 식별되어야 한다. 별도 테스트 Scene은 실제 게임 실행 구성과 공유 가능한 기반을 사용하고 개발 fixture만 분리한다.
- 기존 자산 GUID·`.meta`·직렬화 연결·ID·저장 버전·데이터 호환을 보존한다. 마이그레이션 필요 시 설계를 먼저 제시한다.

## 4. 골격 우선 개발 워크플로

1. RoadMap의 각 단계에서 실제 게임을 관통하는 대표 기능 하나를 정한다. 대량 콘텐츠·유형·미완성 기획을 한꺼번에 완성하지 않는다.
2. 시작 전 **기획 근거(문서 절/도안) → Scene/Prefab 위치 → UI Hierarchy → 소유 상태·규칙 서비스 → 통합 경로 → 검증 항목**을 짧게 제시한다. 별도 승인 항목이 없으면 승인된 범위 내에서 계속할 수 있다.
3. 임시 콘텐츠 수는 최소화하되 최종 게임의 구조적 형태로 구현한다. 일회성 시각화 패널·씬 복제로 '골격'을 대체하지 않는다.
4. 구현 후 ArchitectureStandards의 A~E(기획·편집 구조·책임·통합·저장)를 정적 검토하고 코드·Prefab·Scene 실제 상태로 근거를 남긴다. 각 게이트를 통과/미통과/미확인으로 표기한다.
5. 컴파일 결과를 별도로 기록한다. 기능 테스트(Edit/Play Mode 포함)는 **목적·성공 기준·범위 보고 후 사용자의 명시적 요청·승인**을 받은 경우에만 수행한다.
6. 구조 게이트 통과 + 승인된 기능 검증 통과까지 확인되어야 **해당 단계 골격 완료**로 기록한다. 기능만 동작하면 '기능 프로토타입 통과 / 골격 미완료'로 구분한다.
7. 다음 시스템으로 전환할 때 누적된 1단계 이후 기능이 하나의 실제 게임 구성에서 이어지는지 확인한다. 콘텐츠 유형·시각적 폴리싱은 전체 1~9단계 골격 이후 확장한다.

## 5. 1~7단계 재구성 특별 규칙

- 현행 1~7단계를 구조 재구성 대상으로 지정하며 8단계 진입은 구조 정비 완료 후 결정한다.
- 재구성 요청을 받으면 곧바로 전체 재작성을 시작하지 않고 **현황 감사표(기획 대비 / Scene / UI / 상태 / 서비스 / 저장 / 통합), 대상 파일·자산, 보존·이동·대체 목록, 작업 순서, 위험·승인 필요 사항**을 제시한다.
- 이미 동작하는 도메인 규칙·저장·ID를 가능한 한 재사용한다. 임시 UI만 바꾸면 되는 경우 게임 규칙을 재작성하지 않는다.
- 여러 파일에 걸친 재구성은 대상·영향을 제시해 사용자 승인을 확인한다. 이미 승인한 묶음 안의 통상적인 편집은 파일 수만을 이유로 재승인을 요구하지 않는다. 승인 후 작은 묶음으로 수행하고 중간 단계의 미검증 상태를 과장하지 않는다.
- 개발용 별도 Scene이 최종 게임 Scene을 대체하지 않도록 전환하고 테스트 전용 데이터·UI는 식별해 격리한다.
- 자동으로 전체 테스트, Play Mode, 저장 초기화, 커밋, 푸시, 브랜치 통합을 수행하지 않는다.

## 6. 계획 보고·의사결정

- 작업 계획은 승인 요청 자체가 아니다. 별도 승인 대상이 없는 계획은 보고 후 승인된 범위에서 진행할 수 있다.
- 확정된 기획의 변경, 구조 기준 예외, 구조에 영향을 주는 대규모 변경, 미허가 파일 생성·삭제, 새 패키지·의존성 도입은 사전에 사실·대안·영향을 분리해 보고한다.
- 과거의 미해결 Unity 참조 7개는 사용자의 기존 무시 지시에 따라 선행 차단 조건으로 삼지 않는다. 실제 작업 장애가 확인되면 재현 근거·영향을 보고하고 필요한 조치의 승인 범위를 확인한다. 정상 참조로 판정하거나 임의 수정하지 않는다. 배포·설치 설정은 게임 기능 완료 후 별도 과제다.
- 새 패키지 도입 시 이름·출처·용도·도입 전후 차이·호환·유지보수 영향을 설명한다. 기존 Unity 도구/패키지를 먼저 재사용한다.

## 7. Unity CLI·Editor·에셋

- C# 파일·Git 작업은 일반 CLI를, Scene·Prefab·Component·ScriptableObject·직렬화 연결 작업은 가능한 Unity CLI를 우선한다. 필요한 경우 MCP를 사용한다.
- 대상 Editor·프로젝트를 확인하고 사용자가 작업 중인 Scene을 승인 없이 닫거나 저장·교체하지 않는다. 기존 연결 성공을 이유 없이 반복 조회·재설치하지 않는다.
- `.meta`, GUID, Prefab 연결, Scene 직렬화 참조의 무결성을 보호한다. 임의 YAML 편집보다 Unity API를 우선한다. 에셋 이동 시 GUID 유지와 참조 영향을 확인한다.
- 실행 중인 대상 Editor에서 Hierarchy/Prefab·컴포넌트·직렬화 참조·기존 컴파일 결과를 읽는 작업은 **읽기 전용 정적 조회**다. Editor가 Edit Mode에 있다는 사실이나 조회용 API 호출 자체를 기능 테스트로 취급하지 않는다. 조회를 위한 게임 로직·사용자 명령 실행은 정적 조회에 포함하지 않는다.
- Editor/프로젝트 열기와 Scene/Prefab 로드는 그 자체로 기능 테스트 통과가 아니다. 다만 초기화·임포트·사용자 작업 상태 변경 가능성을 별도로 판단하고 승인된 작업 범위에서 수행한다. 새로 여는 경우 대상과 영향을 사전에 알리며, 단순 조회 요청만으로 사용자 Scene을 닫거나 교체·저장하거나 직렬화 상태를 변경하지 않는다. 메모리상 별도 미리보기 조회도 사용자 작업 상태 보존 조건을 지킨다.
- Unity API·Editor 도구로 UI를 제작하여 Scene/Prefab에 저장하는 작업은 승인된 자산 편집이다. 런타임에 기본 UI 트리를 조립하는 구현과 구별하며, 정적 조회 권한으로 제작·저장을 수행하지 않는다.

## 8. 검증·보고

- 컴파일 오류 조회는 자율적으로 할 수 있다. 빌드는 필요할 때만 실행하며 일반적으로 생략한다. 컴파일/빌드 성공을 런타임 동작 성공으로 주장하지 않는다.
- Edit Mode 테스트 러너·Play Mode 진입·직접 조작·게임 규칙/행동을 호출하는 자동화 기능 테스트는 범위와 성공 기준을 설명하고 명시적 요청 또는 승인 후 실행한다. Editor 연결·읽기 전용 조회·컴파일 확인의 허가를 기능 테스트 승인으로 확대하지 않는다. 승인 검증 범위를 임의 확대하지 않는다.
- 승인 없이 할 수 있는 구조 검사는 파일·컴포넌트·메타·연결의 읽기 전용 확인으로 한정한다. 구조 점검이 기능 테스트를 대체하지 않는다.
- 사용자 테스트 결과를 보고받으면 그 범위만 통과로 기록한다. 다른 Scene·경로·예외까지 자동으로 통과 처리하지 않는다.
- 보고에는 변경 범위, A~E 구조 게이트, 컴파일, 기능 테스트, 저장 호환, 미검증·남은 위험을 구분한다.
- 오류가 있으면 재현 조건·원인/가설·영향·수정·재검증 여부를 구분한다.

## 9. 기록·복구·인계

- State에는 현재 브랜치·중요 결정·진행 상태·미해결 사항·다음 행동을 기록한다. 구조 재구성 중 단계별 상태는 기능 통과와 골격 통과를 구분한다.
- Queue는 요청·명령·수정·오류·핵심 결과를 하나의 작업 ID 세트로 묶는 최근 실행 FIFO이며, `queue_limit` 기본 100이다. 요청/결과 세트를 분리하지 않는다. History는 이관된 원본 기록이다.
- 실제 사용자 지시와 도구 명령·중요 출력은 다음 에이전트가 정확히 재개할 수 있도록 요약하되 의미를 바꾸지 않는다. 누락·부분 요약은 그렇게 표시한다. 인증정보는 기록하지 않는다.
- 명령 시작은 `started`, 결과는 같은 ID에 `completed`와 상태·핵심 출력을 남긴다. 미확인은 `unknown`·중단은 `interrupted`로 기록한다. Queue 기록기 자신의 쓰기는 재귀 기록하지 않는다.
- FIFO 상한 초과 시 가장 오래된 작업 세트 전체를 History 뒤에 원문·ID를 보존해 복사하고 확인한 후 Queue에서 제거한다. 충돌 시 중단해 차이를 보고한다.
- Queue는 모든 새 세션에서 필수로 열지 않는다. 재개·인계·진행 근거 조회에 필요할 때 해당 부분만 읽는다. 다른 기기로 인계하는 기준은 사용자가 승인해 공유한 최신 커밋이다.
- 커밋되지 않은 기록·작업은 자동 동기화된 것으로 가정하지 않는다. 인계를 핑계로 자동 커밋·푸시하지 않는다.
