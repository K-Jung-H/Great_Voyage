# Architecture Standards — 신규 개발 및 1~7단계 재구성 기준

상태: 규범 문서. 사용자 적용 이후 신규 코드와 기존 구조의 개편에 적용한다. 이 문서는 게임 기획을 변경하지 않으며 `GameDesign.md`와 원본 기획·도안을 대체하지 않는다. `Architecture.md`의 과거 구현 기록과 충돌하면 **앞으로의 구현 구조에 관해서만** 이 문서를 우선한다.

## 1. 지향점과 경계

- 목표는 눈으로 동작을 확인할 수 있는 일회성 데모가 아니라 **최종 게임의 공간·화면·상태 흐름을 축소한 실행 가능한 기반**이다.
- 대표 기능 하나만 구현하되 그 기능을 담는 객체 계층, 데이터 계약, 책임 경계, 확장 지점은 최종 요구사항과 호환되어야 한다.
- 미완성 UI는 공백·플레이스홀더를 허용한다. 그러나 기획서에서 정한 주요 영역·정보의 위치·이동 경로는 임의로 한 덩어리 패널로 축소하지 않는다.
- Scene 수, 서비스 수, 추상 클래스 수를 미리 고정하지 않는다. 각 요소의 수명과 소유권에 따라 가장 작은 유지보수 가능한 구성을 택하고 결과를 문서화한다.
- 기존 프로젝트의 게임 규칙과 저장 호환성을 우선 보존한다. 코드를 다시 작성하는 것 자체를 목표로 삼지 않는다.

## 2. Scene 및 Hierarchy 표준

### 2.1 역할 분리

Scene/Prefab의 역할을 먼저 정의한다.

- **Bootstrap/Composition Root:** 시작·의존성 연결·게임 세션 초기화. 한 실행 흐름에서 중복 생성되지 않는다.
- **Game/World:** 플레이어가 이동하는 세계, 함선·항구 구역 및 그 연결. 실제 공간 전환 규칙을 따른다.
- **World Content:** 함선 층, 벽, 계단, 시설, 상호작용 지점, 항구 구역 등 독립적으로 편집할 공간 콘텐츠. 적절한 Scene 또는 Prefab 단위로 재사용한다.
- **UI Root:** 공통 HUD, Overlay, 주요 화면, 모달을 관리한다. UI 표시와 게임 규칙은 분리한다.
- **Test Fixtures:** 테스트를 위해 특수 인물·자원·조건을 부여하는 별도 설정 또는 장면. 게임의 실제 Composition Root를 복제해 또 다른 구현을 만들지 않는다.

Bootstrap 단일 Scene, Additive Scene, Prefab 기반 전환 중 무엇을 사용할지는 현재 엔진·기획의 공간 수명과 저장 복원 요구를 분석해 제안한다. **도구 사용 편의를 이유로 형식만 있는 다중 Scene 체계나 Scene 복제를 일괄 도입하지 않는다.**

### 2.2 공통 Hierarchy 계약

다음은 개념적 책임 구분이며 실제 최종 이름·GameObject 수를 강제하지 않는다.

```text
GameRoot
├── Systems
├── World
│   ├── Ship
│   └── Port
├── Characters
├── Cameras
└── UIRoot
    ├── HUD
    ├── Screens
    └── Modals
```

- System은 자신의 상태와 생명주기를 명확히 소유한다. 같은 GameSession/SaveService가 개발 씬마다 상이한 구성을 갖지 않게 한다.
- Ship은 층·시설과 논리 상태의 관계가 명확해야 한다. Port는 기획서의 구역·통로·포털 관계를 표현할 수 있어야 한다.
- 플레이어·선원은 인스턴스 수명과 화면/층 전환 규칙을 구분한다. 세계 상태가 화면 전환으로 소실되면 안 된다.
- 반복 활용하는 월드 오브젝트는 Prefab으로 관리하고 실제 배치·참조를 Editor에서 검사할 수 있어야 한다.
- 생성되는 동적 캐릭터·시설은 해당 부모 루트와 안정 ID에 귀속된다. 임의의 최상위 GameObject를 만들어 방치하지 않는다.
- 단일 Scene 복제 방식은 독립 상태·UI·서비스의 중복을 야기하면 금지한다. 기존 CaptainsCabin/CrewPrototype/PortPrototype은 통합 전환 대상으로 분류한다.

### 2.3 Scene 계약서

각 신규/변경 Scene에는 해당 문서 또는 가까운 기술 명세에 다음을 남긴다: 역할, 진입/종료 조건, 소유 시스템, 포함된 공간·UI, 외부 의존성, 전환 중 유지되는 상태, 저장 슬롯 정책, 테스트 전용 요소. 실질적 이유 없는 거대 Hierarchy나 동일 시스템 중복 배치를 피한다.

## 3. UI 제작의 필수 규칙

1. **화면을 구성하는 Canvas, RectTransform, Panel, Button, Text/TMP, Scroll View, Layout Group 등 기본 계층은 사전에 Unity Editor의 Scene/Prefab에 배치한다.**
2. 화면 Controller는 `[SerializeField]` 등 명시적 직렬화 참조로 기존 컴포넌트에 연결한다. 런타임에 UI 화면 전체의 객체 트리를 `new GameObject`로 만들거나 수동 좌표에 조립하지 않는다.
3. 반복되는 선원 항목·상품 행·계약 행·로그 항목만 사전 정의된 Item Prefab에서 데이터 수만큼 동적으로 생성할 수 있다. 풀링 여부는 실제 필요에 따라 결정한다.
4. 런타임에서 허용되는 것은 내용 갱신, 활성화, 선택, 데이터 바인딩, 애니메이션, 동적 목록 채우기다. UI 화면의 기본 계층·레이아웃은 코드가 소유하지 않는다.
5. 일회성 개발 디버그 오버레이는 본 게임 UI와 분리해 명확히 표시하며 사용자 승인 없이 게임 화면을 대신하지 못한다.
6. 기획서의 UI 도안(D/E 자료), 영역의 상대 배치, 필수 정보와 핵심 상호작용 흐름을 초기 골격부터 반영한다. 확정되지 않은 예시 장식·기능은 추가하지 않는다.
7. UI와 규칙 처리 코드를 분리한다. Controller는 화면 상태 표시와 명령 전달을 맡고, 구매·계약·업무·저장 변경은 해당 도메인 시스템이 수행한다.
8. 해상도·앵커·레이아웃 그룹·팝업 쌓임 순서·입력 차단·정지 소유권을 구조 단계에서 확인한다. 완성된 미술·애니메이션은 후속 단계로 미룬다.
9. 누락된 직렬화 참조, 잘못된 UI 부모 관계, 이름만 같은 중복 객체는 완료 전 정적으로 점검한다.

## 4. 시스템과 데이터 경계

- **Definitions:** 상품·시설·선원 유형·함선과 항구 등 제작 시 정의 데이터(ScriptableObject 등).
- **Runtime State:** 선원 개체, 계약, 위치, 시설 내구도, 항해 기록 등 변경 가능하고 저장 대상인 데이터.
- **Domain Systems:** 구매/판매, 계약 정산, 업무 선점, 항해, 일지 등의 규칙과 유효성 검사를 소유한다.
- **Presentation:** Scene 오브젝트·Sprite·UI·카메라 등의 표현. 도메인 상태의 유일한 원본이 되지 않는다.
- **Composition/Flow:** 시작·화면/공간 전환·시스템 간 이벤트와 초기화 순서를 조율한다. 도메인 규칙을 중복 구현하지 않는다.
- 공용 관리자 하나에 UI 구성·경제·AI·저장·입력 등을 누적하지 않는다. 반대로 기능 하나당 인터페이스·클래스를 무조건 만드는 과설계도 금지한다.
- 새 콘텐츠 유형 1개를 추가할 때 수정이 필요한 코드·자산 범위를 명시해 확장성을 검토한다. 기존 조건문 수정이 필요한 부분은 그 이유를 설명한다.
- UI 종류와 Scene 개수가 늘어도 동일 저장/계약/항해 원본을 사용해야 한다. 프로토타입별 서로 다른 세계 상태 모델을 만들지 않는다.

## 5. 최소 골격의 수용 기준

**A. 기획 적합성:** 해당 단계의 필수 화면 영역·공간 연결·행동 흐름이 기획 자료와 대응한다. 시각 자산과 콘텐츠는 임시 가능.

**B. 편집 가능 구조:** Unity Editor Hierarchy/Prefab에서 공간·화면 계층이 확인되고 재배치·재사용 가능하다. 기본 UI의 코드 동적 조립이 없다.

**C. 책임과 확장성:** 상태·규칙·표현·흐름을 구분하고 추가할 대표 유형의 확장 경로가 명확하다.

**D. 실제 게임 통합:** 동일한 공통 게임 진입 흐름에서 이전 단계와 현재 단계가 이어진다. 별도 테스트 씬 하나의 성공만으로 통합 완료로 표시하지 않는다.

**E. 저장 일관성:** 기존 슬롯 보호, 저장 데이터의 소유자·복원 순서, 버전 호환·미완료 상태 처리 방침이 명확하다.

**F. 검증 구분:** A~E의 정적 구조 점검, 컴파일 확인, 기능 테스트를 각각 기록한다. 기능 테스트는 사용자 승인 전 실행하지 않는다.

각 게이트의 통과/미통과/미확인을 명확히 기록한다. 구조 미통과 시 동작이 정상이어도 해당 단계를 **기능 프로토타입 통과, 골격 미완료**로 표기한다.

## 6. 1~7단계 재구성 원칙

1. 기존 Scene·Prefab·코드·SaveData 버전·파일 경로·GameDesign을 실제로 조사한다. 현재 기획과 UI 도안의 해당 항목을 직접 대조한다.
2. 기능별로 **보존 / 구조 이동·연결 / 교체 / 미구현 / 판단 필요**로 분류한다. 시각적 차이와 구조적 차이를 구분한다.
3. 목표 Scene/Prefab 트리와 각 UI 화면의 편집기 계층안을 작성한다. 상이한 대안을 비교하고 다수 파일 이동·공유 인터페이스 변경 등의 영향이 크면 사용자 승인 전 실행하지 않는다.
4. 이전 SaveData·ID·경로가 손실되지 않도록 호환/마이그레이션 전략을 수립한다. 필요하면 백업·검증 계획을 제시하되 저장 삭제를 임의 실행하지 않는다.
5. **공통 진입점·UI 기반 → 플레이어·함선·항구 공간 → 기존 도메인 서비스 연결 → 개별 화면 연결 → 1~7단계 대표 흐름 통합** 순으로 구조를 정비한다. 세부 순서는 실제 의존성을 보고 조정한다.
6. 사용자가 승인한 범위에서 작은 변경 묶음으로 구현한다. 각 묶음은 구조 점검과 컴파일 결과를 기록하고 기능 테스트는 별도 승인받아 수행한다.
7. 1~7단계에 없는 새 게임 콘텐츠·기능을 임의 구현하지 않는다. 재구성이 끝나고 해당 단계의 구조/통합/기능 게이트를 확인한 뒤 8단계로 진행한다.

## 7. 금지되는 지름길

- 버튼만 누르면 동작한다는 이유로 최종 UI 계층을 무시한 단일 텍스트 패널을 완료 화면으로 선언.
- 독립 프로토타입 씬마다 서비스·세이브·UI를 복사해 서로 다른 구현으로 유지.
- 임시 데모를 빨리 구성하려고 기획서의 공간·지도·창구 진입 구조를 생략.
- 런타임 기본 UI 트리 생성 코드를 임시로 추가한 뒤 최종 구조로 간주.
- 구조 재구성을 빌미로 작동 중인 도메인 규칙·저장 데이터를 근거 없이 전면 재작성.
- 테스트 미승인 상태에서 Play/Edit Mode 검증을 자율 시행하거나, 구조 점검을 기능 테스트 통과라고 보고.

## 8. 현재 구현에 대한 적용 지침

- `PortPanel` 등 코드에서 전체 UI 객체를 조립하는 화면은 **Editor 배치 UI + 직렬화된 화면 Controller**로 전환한다. 기존 경제 규칙은 최대한 재사용한다.
- `CaptainsCabin`, `CrewPrototype`, `PortPrototype`을 실제 게임 구성과 테스트 Fixtures로 구분하고, 복제된 시스템·UI·세션 설정이 있는지 감사한다.
- `CrewSimulation` 등 책임이 집중된 구성은 변경 영향과 실제 확장 필요성을 분석한 후 필요한 역할만 분리한다. 단순 줄 수만으로 재작성하지 않는다.
- `Journal`의 지도 표현은 실시간으로 생성되는 선/점 데이터처럼 동적 메시가 필요한 경우를 허용하되, 일지 화면의 기본 패널·영역·조작 UI는 에디터 기반으로 유지한다.
