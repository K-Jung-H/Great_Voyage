# RoadMap — 실제 게임 골격 중심 개발

기준: 2026-10-19. 이 문서는 기존 게임 기획의 개발 순서를 보존하며, **과거 구현 완료 기록과 신규 골격 수용 기준을 구분**한다. 기존 커밋의 사실은 State/Queue/History에서 확인한다. 현재 1~7단계의 기능별 구현·테스트 기록은 폐기하지 않지만 새 표준의 구조/통합 수용을 의미하지 않는다.

## 진행 원칙

- 0단계 준비 → 1~9단계 **각 시스템의 대표 기능을 실제 게임 골격에 연결** → 10단계 콘텐츠·기능 유형 확장 → 11단계 PC 완성 → 12단계 모바일 입력.
- 대표 기능은 한 개로 제한할 수 있다. 단, Scene/Prefab 계층, UI 영역, 상태·규칙 소유권, 실제 게임 흐름과의 통합은 후반 단계로 미루지 않는다.
- 모든 단계의 수용 게이트는 `ArchitectureStandards.md`의 A(기획), B(Editor 구조), C(책임·확장), D(통합), E(저장), F(검증 구분)이다.
- **구조 점검 + 컴파일 + 사용자 승인 기능 테스트**를 각각 기록한다. 임시 모형에서의 단독 동작은 기능 프로토타입 통과이지 골격 완료가 아니다.
- 미술, 애니메이션, 완성 콘텐츠와 밸런스는 후속으로 미룰 수 있으나, 전체 확정 UI Frame은 U0에서 후속 기능보다 먼저 제작한다. 공간 진입 구조는 해당 시스템의 최초 구현에 반영한다.
- GameDesign의 도안/구성 표를 각 단계의 요구사항으로 참조한다. 확정되지 않은 예시 콘텐츠를 근거 없이 추가하지 않는다.

### UI Frame 선행 기반 — 2026-10-20 개정안

- [ReconstructionPlan 6·9·14절](ReconstructionPlan.md)의 U0에서 전체 게임 UI Frame을 Editor Scene/Prefab으로 먼저 제작한다. S1 기존 실행 기반 위에 U0를 추가하고, 구조 수용 및 S1 기능 검증 후 S2로 진행한다. 2026-10-20 사용자 승인으로 미니게임(F20 Host 포함)을 제외한 U0 Frame을 제작했다. 실제 결과는 ReconstructionPlan15절이다. 기능 검증/후속 단계 승인은 별도다.
- 8~12단계 화면도 Frame은 U0 대상이다. 아래 단계의 화면 구성/배치 항목은 U0 결과를 사용하는 Controller·데이터·입력·시스템 연결 및 검증으로 해석한다. 후속 기능 전체 선행 구현을 요구하지 않는다.
- 구조 완료는 실제 편집 가능한 컴포넌트·계층·반복 행·배치·참조로 판단한다. 기능 완료는 각 단계 A~F 및 승인 테스트로 별도 판단한다. 미니게임은 최신 사용자 지시로 이번 U0 수용에서 제외한다. 완료 표기는 미니게임 제외 Frame으로 한정한다.

### 단계별 수용 범위의 해석

- 이 문서의 단계 번호가 실행 기준이다. GameDesign 보존 원문 15절의 큰 단계와의 대응은 GameDesign 안내부를 따른다. 게임 규칙은 GameDesign, 신규 구조는 ArchitectureStandards를 따른다.
- 각 단계의 대표 기능·구조·완료 항목은 현재 필수 범위다. A~E는 그 범위와 이미 연결된 이전 기능에 적용하고 F에 따라 구조·컴파일·기능 검증을 구분한다. 제외된 후속 기능 전체의 완성을 선행 조건으로 요구하지 않는다.
- 후속 기능을 위한 연결점은 필요한 상태·인터페이스·진입 영역·복원 경계가 준비되었는지 확인한다. 연결점 준비는 해당 후속 기능의 동작 통과가 아니다. 후속 단계에서 실제 연결·저장·기능 검증을 완료한다.
- 후속 콘텐츠·미술·규칙 확장은 유보할 수 있으나 현재 필수 화면 구획·공간 연결·공통 실행 흐름·저장 호환은 유보할 수 없다. 후속 의존 항목은 담당 단계와 검증 대기로 기록하고 필수 항목의 미통과/미확인과 구별한다.
- 새 구조를 감사하지 않은 과거 기능 통과는 골격 완료로 간주하지 않는다. R4는 1~7단계의 위 필수 범위 통과를 요구하며 8단계 이후 사건·전투·전체 콘텐츠 검증을 선행 요구하지 않는다.

## 현재 최우선 작업 R. 1~7단계 구조 재구성

상태: **신규 표준에 따른 구조 감사 및 재구성 필요.** 7단계 사용자 직접 수정·테스트·커밋 사실은 2026-10-20 사용자 지시로 확인했다. Git에서 `0e9c96d7b41f836ba0df664c7d0f4805ff35541f` (`roadmap step 7 complete`, 2026-10-19)을 확인했다. 개별 테스트 시나리오·결과·범위는 미확인이며 전체 통과로 추정하지 않는다. 과거 검증 결과를 취소하거나 새 구조 게이트 통과로 승격하지 않는다.

### R0. 현재 상태 감사

- CaptainsCabin, CrewPrototype, PortPrototype의 Hierarchy, 시스템 루트, 동일 역할 객체의 복제, Scene 간 전환, 시작과 저장 슬롯을 파악한다.
- 게임 기획의 공간 도안·UI 레이아웃을 실제 Scene/Prefab과 1:1로 비교한다.
- 현재 생성형 UI 화면, 단일 문자열 패널, 데이터/규칙/표현 책임 혼재, 환경별 설정 중복을 식별한다.
- 결과: **기획 항목 / 현 구현 / 차이 / 보존·이동·대체 / 관련 파일·씬 / 위험 / 승인 필요** 표.

### R1. 목표 구성과 안전한 전환 계획

- 실제 게임용 시작·공간·UI 구성, 공유 Scene/Prefab의 역할과 Hierarchy, 테스트 전용 fixture를 정의한다.
- 기존 GameSession/ShipLayout/NavigationSession/CrewSimulation/EconomySession/JournalSession의 상태 소유권·생명주기를 대조해 중복을 피한다.
- 저장 데이터·ID·슬롯·버전 호환 전략과 각 변경 묶음의 롤백/검증 대책을 명시한다.
- 구조 전면 변경 및 추가/삭제/이동 파일 목록은 승인받은 뒤 구현한다.

### R2. 공통 실행 기반과 에디터 UI 재구성

- 독립 테스트 씬 복제 없이 공통 게임 시작과 공간 전환을 연결한다.
- U0에서 HUD·일지·거래·고용·계약뿐 아니라 이벤트·전투·무장·조선소·시청 등 전체 확정 UI Frame과 반복 요소를 에디터 Scene/Prefab으로 선행 구성한다. 임시 콘텐츠도 기획서의 구획·정보 흐름에 맞게 배치한다.
- 화면 Controller는 에디터 배치된 컴포넌트를 참조하고, 도메인 규칙 호출·상태 표현만 담당한다.
- 임시 테스트 전용 UI·리셋 기능은 제품 UI에서 분리한다. 기존 구현 기능과 세이브를 보호한다.

### R3. 1~7단계 실제 게임 흐름 복구

- 플레이어 이동·상호작용 → 선내 층/시설 → 시간·저장 → 출항·항구 구역 → 선원 일과 → 거래·고용·계약 → 일지·조타·취침을 같은 실행 구성에서 연결한다.
- 각 단계의 대표 기능과 기획 화면·공간 경로를 대조하고 A~F 게이트를 개별 기록한다.
- 유효한 기존 도메인 로직은 재사용하고 구조와 관계 없는 게임 콘텐츠 추가는 하지 않는다.

### R4. 전환 종료

- 사용자가 명시 승인한 범위에서만 Play/Edit Mode 기능 시나리오를 검증한다. 기존 저장 복원과 핵심 흐름을 반드시 검증 계획에 포함한다.
- 1~7단계가 구조·통합·기능 게이트를 통과한 경우에만 8단계로 재개한다. 미통과는 별도 항목으로 남긴다.

## 0. 준비 — 기반 설정

- 최종 기획서, 원본 이미지/도안, Unity 프로젝트·패키지, CLI/Pipeline, 기존 AGENTS 문서 역할을 확인한다.
- 프로젝트 운영/검증 권한은 Rules에 따른다. 미해결 참조 7개는 사용자의 기존 무시 지시를 유지하며 선행 차단 조건이 아니다. 배포 설정은 제외한다.

## 1. 플레이어 이동과 첫 상호작용

- 대표: 선장실에서 플레이어 이동·벽 충돌·책상 상호작용·일지 열기/닫기.
- 구조: Player Prefab, 공간 루트, 충돌/상호작용, 카메라, 에디터 배치된 일지 진입 UI와 입력 차단.
- 완료: 실제 게임 구성을 통해 이동/상호작용이 동작하며 UI 계층과 상태 소유권이 분리된다.
- 제외: 전체 항해일지 콘텐츠, 모든 UI, 전체 선원 행동.

## 2. 시간·정지·저장/복원

- 대표: 하루 600초 진행, 중첩 정지 사유, 플레이어 위치·층·시간의 저장/복원.
- 구조: 세션 상태, PauseService, 버전·ID 기반 SaveData/SaveService, 화면에 귀속된 정지 핸들.
- 완료: 공통 게임 진입 구성에서 종료·재개가 되고 UI 중첩 시 정지가 정확히 유지된다.
- 제외: 아직 존재하지 않는 계약/이벤트 결과. 이후 기능 상태는 개별 단계에서 저장에 연결.
- 층 상태의 실제 왕복·복원 검증은 3단계에서 확장한다. 2단계의 위치·공간 식별/복원 기반을 완료하기 위해 아직 없는 다층 시스템을 선행 구현하지 않는다.

## 3. 함선 층과 시설 배치

- 대표: 2층 개발 함선, 양방향 계단, 침대 1종, 점유·접근 경로.
- 구조: 층 외형/벽·계단·시설의 편집 가능한 Prefab·Hierarchy, 공통 Cell 단위, 정의/상태 구분.
- 완료: 층 전환·충돌·시설 점유·위치 유지·저장이 공통 실행 흐름에서 작동.
- 제외: 전체 시설 종류·조선소 편집 UI. 이들 확장 경로는 남긴다.

## 4. 수동 항해와 출입항

- 대표: 방향타 조작, 출항·해상 이동·자동 입항, 개발 항구 2개.
- 구조: 선내/해상 좌표 분리, 항구/선착장 공간 연결, 방향타/항구 진입 오브젝트, 항해 완료 안정 ID.
- 완료: 실제 게임 공간의 출항·입항 흐름에서 중복 완료 없이 위치·시간·저장이 이어짐.
- 제외: 자동 조타, 무작위 세계, 바람과 전체 항구 콘텐츠.

## 5. 선원과 시설 업무·생활

- 대표: 정비 선원, 시설 선점과 수리, 식사·취침·배회, 다른 층의 진행.
- 구조: 선원 정의/개체 상태/업무 규칙/이동 표현의 명확한 책임, 캐릭터 Prefab, 업무 대상과 자격·저장 규약.
- 완료: 실제 게임 실행에서 선원 1~2명이 중복 선점 없이 일하며 화면 전환·저장에도 일관성을 유지. 새 업무/특기 추가 경로를 명시.
- 제외: 전체 직업·특기·능력·인물 콘텐츠.

## 6. 항구 거래·고용·계약 첫 순환

- 대표: 상품 1종 구매/판매, 후보 1명 N회 선불·후불 고용, 항해 만료·정산·재고용.
- 구조: 항구 구역·상인·대행인·주점 진입점과 기획서의 각 UI 구획을 에디터에 별도 화면/Prefab으로 제작. 경제 상태와 계약 규칙은 UI에서 분리.
- 완료: 항구에서 실제 상호작용하여 거래·고용·정산하고 항해 후 계약 상태가 저장·복원됨. 재고용 목록과 최종 게시판 UI의 구분을 수용할 데이터/화면 경계가 존재.
- 제외: 전 상품·전 후보·모든 경제 변동·최종 미술. **거래/고용/게시판의 화면 구조 자체는 제외하지 않는다.**
- 현재 필수는 대표 거래·고용·정산·재고용과 편집 가능한 화면 구획·진입 경로다. 협상·주민 요청·전체 과거 고용 콘텐츠의 규칙 확장은 10단계로 남기되 필요한 화면 영역·데이터 경계를 보존한다.

## 7. 항해일지·자동 조타·취침

- 대표: 일지 지도·기록·계획·메모, 자격 있는 선원의 조타, 침대 취침·불침번 연결점.
- 구조: 기획 D/E 자료의 좌측 과거 기록, 중앙 지도, 우측 정보·메모 및 닫기 영역을 Editor UI로 구성. JournalState/규칙과 지도 표시·입력 분리.
- 완료: 실제 게임에서 기록·계획·조타·취침·입항·저장이 연결되고 계획선만으로 자동 이동하지 않으며 기록 이월 규칙 유지.
- 제외: 사건 생성·시작 체크포인트(8단계). 예시 이미지의 미승인 버튼·장식은 구현하지 않는다.
- 현재 필수는 기록·계획·조타·취침·입항·이월·저장 흐름과 불침번/사건 경계 연결점이다. 실제 사건 발생에 따른 취침 중단·미기록 사건 소실·불침번 사건의 연결 검증은 8단계 이후 해당 사건 구현에서 수행하며, 연결점만으로 기능 통과를 기록하지 않는다.

## 8. 이벤트 진행과 결과 저장

- 선행: **재구성된 1~7단계의 구조·통합/기능 게이트 통과**.
- 대표: 폭풍 사건 하나, 이벤트 ID·판정 난수·시작 체크포인트·선택·종료 결과 저장.
- 완료: 같은 사건 시작과 난수 조건으로 복원하고 결과가 중복 반영되지 않으며 취침 중단/일지 기록과 연결.
- 제외: 다종 사건 콘텐츠와 전투.

## 9. 관전 전투·포로 처리

- 선행: 선원·재고·계약·이벤트 체크포인트의 통합.
- 대표: 해적 사건, 자동 전투, 승패·약탈, 포로 수용·인계 및 저장.
- 완료: 관전/카메라/무장·전투 상태 UI가 기획 구조에 맞게 배치되고 결과가 한번만 적용되며 복원 가능.
- 제외: 플레이어 전투 조작, 전투 종류 대량 추가.

## 10. 전체 기능 유형·콘텐츠 확장

기본 골격 통합 이후 각 시스템별로 아래 순서대로 기능을 확장한다. 관련 UI의 **전체 Frame**은 U0에서 선행 제작되어 있어야 하며 이 단계에서는 기능을 연결한다. 기획 미정의 확정 절차는 ReconstructionPlan14절을 따른다.

1. 시설·조선소: 필수 시설 전체, 설치·내구도·수리, 편집·함선 교체.
2. 선원·고용: 특기·경력·소망·행복·신뢰·협상, 다양한 업무, 현재/과거 게시판 재고용.
3. 항구·경제: 기획의 구역 D08~D12, 상품·가격·수요, 주민 요청·시청·평판.
4. 초기 이벤트: 쥐·폭풍·해적·무인도·반란, 경비/망루/망원경과 결과 연계.
5. 후속 콘텐츠: 크라켄·물고기·게·따개비, 낚시·보드게임 등 확정 범위.
6. 전체 게임 시작/순환: 시작 항구·선원0명·초기 자금, 모든 UI 진입, 저장·게임 오버와 반복 항해.

미정 값은 위임된 조정값과 구별한다. 전체 A01~A28 수용 항목의 누락 여부를 점검한다.

## 11. PC 완성도

- 최종 그래픽·애니메이션·오디오·표현 단위·반응형 UI·조작감·밸런스·장기 진행 검증.
- 기존 Editor 구조와 도메인 시스템을 유지하며 임시 자산을 교체한다. 새 UI 구조를 이 단계에서 처음 만드는 것은 허용하지 않는다.

## 12. 모바일 입력

- PC 게임 흐름 완성 뒤 미리 확보한 조이스틱/상호작용 영역에 모바일 입력을 연결하고 지도·창·화면 크기를 대응한다.
- PC 조작을 모바일용 입력 구성으로 강제 대체하지 않는다.
