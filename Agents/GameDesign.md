# 대항해 · Great Voyage

- 가제: 대항해(Great Voyage)
- 문서 버전: 1.0 / 2026-10-18
- 목적: 사용자가 의도한 게임 규칙·공간 구성·그래픽 방향을 보존하면서 Unity에서 단계적으로 구현한다.
- 상태: 합의된 기획의 최종 통합본. 수치 밸런싱과 명시적으로 위임된 세부 설계는 구현 중 구체화한다.
- 대상: 구현을 담당하는 Codex, 게임 기획자, UI·그래픽 제작자.

## 1. 문서 사용 원칙

### 1.1 결정의 구분

| 표시 | 의미 | 구현 시 처리 |
|---|---|---|
| 확정 규칙 | 원문과 후속 대화에서 사용자가 확정한 동작 | 임의 변경 금지 |
| 초기 콘텐츠 | 사용자가 채택한 최초 콘텐츠 구성 | 해당 기반이 완성된 단계에서 추가 |
| 구현 기준 | 확정 규칙을 안정적으로 실행하기 위한 구조·검증 기준 | 기술적 실현 방식은 구현자가 선택 |
| 임시 수치 | 초기 자금, 비율, 확률, 비용, 시간, 기준값 등 밸런스 데이터 | 외부 설정으로 분리하고 마지막 단계에서 조정 |
| 구현 중 구체화 | 이번 기획에서 상세 확정을 하지 않기로 한 사항 | 기존 규칙을 바꾸지 않는 범위에서 설계·기록 |
| 후속 단계 | 기반 완성 이후 또는 향후 확장 사항 | 현재 단계의 완료 여부와 구분 |

사용자가 제시한 하루 10분, 약탈 범위 등의 수치는 본 문서의 기준값으로 구현한다. 초기 자금 등 지정하지 않은 값은 임시값을 설정할 수 있다. 수치를 조정 가능하게 만든다는 이유로 최초부터 사용자 지정값을 다른 값으로 대체하지 않는다.

### 1.2 자료의 역할과 우선순위

1. 게임 규칙은 본 문서에 통합된 최신 사용자 결정이 우선한다.
2. 도안은 공간의 연결·UI 영역·상대 배치 기준이다.
3. 예시 인게임 이미지는 도안이 게임 화면에서 어떻게 구성되는지 보여 주는 참고다.
4. 실제 플레이의 화풍·시점·유닛 디자인은 최종 그래픽 레퍼런스를 따른다.
5. 원문 아이디어 노트는 배경 자료다. 본 문서와 충돌하는 과거 규칙을 복원하지 않는다.

예시 인게임 이미지에만 있는 스킬 버튼, 치유 마법, 골드 추가 버튼, 실제 지명, 수치, 자동 항해 버튼 등은 기능 확정의 근거가 아니다. 예시 이미지의 입체적인 배경과 세부 묘사를 실제 플레이의 최종 화풍으로 채택하지 않는다.

### 1.3 구현자 권한

기존 규칙을 바꾸지 않는 세부 알고리즘, 자료구조, 입력 키, 임시 콘텐츠 수량과 수치는 구현 중 정할 수 있다. 선택한 내용은 구현 기록에 남긴다. 확정된 규칙·화면 구도·콘텐츠 단계가 달라지는 경우에만 사용자 확인을 받는다. 시작 콘텐츠의 상세 세계관, 미니게임 규칙 등을 모두 미리 확정하기 위해 기반 구현을 중단하지 않는다.

## 2. 게임 개요와 플레이 구조

### 2.1 기본 사양

| 항목 | 내용 |
|---|---|

### 2.2 핵심 경험

플레이어는 항구별 수요와 가격 차이로 이익을 얻고, 선원을 고용해 함선을 운영한다. 항해 중에는 방향타 조정, 항해 일지 기록, 낚시, 선내 경비와 대화 등을 수행한다. 선원의 행복도·신뢰도, 식량, 기능 타일 내구도, 계약 지급을 관리하면서 함선을 개조하거나 교체한다.

### 2.3 주요 반복 흐름

항구 정보 수집·거래 → 선원 고용·계약 확인 → 식량·시설·장비 준비 → 출항 조건·후불금 검사 → 항해·일과·이벤트 → 자동 입항 → 거래·정비·계약 정산·재고용 → 다음 항해.

항해 1회는 항구를 떠난 시점부터 항구에 도착한 시점까지다. 출발 항구와 도착 항구가 같아도 1회로 인정한다. 명성 부족으로 게임 오버가 되는 경우를 제외하고 전투 패배 자체가 플레이 종료를 뜻하지 않는다.

### 2.4 시작 조건

- 시작 항구는 무작위로 정한다.
- 시작 함선은 고정된 모델을 사용한다.
- 시작 선원은 없다. 혼자 출항할 수 있다.
- 시작 자금을 지급한다. 금액은 임시 밸런스 값이다.
- 항구 이름·개수, 시작 모델의 세부 배치와 상품 수량은 구현 중 정한다.
- 최초 작동 확인용 콘텐츠는 핵심 흐름을 실제로 실행할 수 있도록 구성한다. 상세 시작 콘텐츠 설계를 이번 문서의 선행 조건으로 삼지 않는다.

## 3. 그래픽·시점·캐릭터 기준

### 3.1 플레이 화면

- 배경: 림월드식 탑뷰, 명확한 방·타일·통로 구분, 읽기 쉬운 사물 형태와 외곽선.
- 유닛: Prison Architect식 Head / Body / Hand 구성의 SD 캐릭터.
- 이동·행동 상태는 단순한 유닛 형태에서도 구분되어야 한다.
- 예시 이미지의 다리까지 세밀하게 표현된 RPG 캐릭터를 최종 유닛 기준으로 사용하지 않는다.
- 도안에서 정한 가로 방향 함선 구도와 공간 배치를 실제 탑뷰 표현으로 옮긴다.

### 3.2 인물 일러스트

대화·고용·거래 등에서 사용하는 전신 인물 일러스트의 화풍은 게임 『대항해시대 5』의 캐릭터 일러스트를 참고한다. 화면 영역에 따라 상반신 중심으로 잘라 표시할 수 있다. 실제 플레이 유닛과 별도의 자산 체계로 관리하고, 같은 인물의 외형 특징은 대응시킨다.

『대항해시대 5』의 개별 참고 이미지는 이번 첨부 자료에 포함되어 있지 않다. 해당 명칭은 사용자가 지정한 화풍 방향이며, 본 문서가 특정 캐릭터 그림이나 세부 스타일 분석을 확정한 것은 아니다.

### 3.3 지도

최종 지도 레퍼런스의 종이 질감, 절제된 육지·바다 색상, 간결한 지형 구분을 적용한다. 가상 세계를 사용하며, 예시 이미지의 리스본·뉴욕 등 실존 도시와 지형은 콘텐츠로 자동 채택하지 않는다. 지도에는 현재 위치, 경로, 항구, 이벤트 기록과 레이어가 명확하게 읽혀야 한다.

### 3.4 UI 표현

도안의 영역과 상대 위치를 보존한다. 예시 이미지의 해양 시대 분위기, 프레임·패널 구성은 참고할 수 있지만 장식이 시인성과 조작을 방해하지 않도록 한다. 가로형 화면을 기본 구성으로 삼고 해상도 변화에 따른 여백·패널 크기 처리는 구현 중 구체화한다.

## 4. 화면·공간 명세

### 4.1 기본 HUD

| 위치 | 요소 | 규칙 |
|---|---|---|
| 좌측 상단 | 보유 골드 | 실제 보유액 표시 |
| 좌측 중단 | 수주 중 퀘스트 | 진행 상황 표시 |
| 상단 중앙 | 항해 일자 | 항해 중에만 활성화. 일지 열기 버튼이 아님 |
| 우측 상단 | 게임 날짜·시간대 | 낮·저녁·밤 등 시간 흐름 시각화 |
| 좌측 하단 | 이동 조이스틱 배치 | 모바일 입력용 영역을 준비 |
| 우측 하단 | 상호작용 버튼·조이스틱 배치 | 모바일 입력용 영역을 준비 |

PC는 키 입력으로 움직이고 상호작용한다. 구체적인 키 배치와 카메라 확대·축소 지원은 구현 중 구체화한다. 모바일용 UI가 있다는 이유로 PC에서 조이스틱 조작만 강제하지 않는다.

### 4.2 함선과 층 전환

- 한 화면에는 하나의 층만 렌더링한다.
- 평상시 카메라는 플레이어 캐릭터를 따라간다.
- 층 이동 타일과 상호작용하면 해당 층으로 이동한다.
- 층별로 다른 전환 일러스트를 사용한다.
- 렌더링하지 않는 층의 선원·업무·시설 상태도 지속 관리해야 한다.
- 선내 구조도는 상갑판, 주갑판 내부, 화물창, 하부 선창의 구조 참고다. 모든 함선과 시작 함선을 무조건 4층으로 고정하는 명령이 아니다.
- 함선별 크기·층수·고정 타일·배치 가능 구역을 데이터로 정의한다.

### 4.3 항구 맵

| 도안 | 공간 구성 |
|---|---|
| 항구 도안 1 | 함선과 선착장, 육지로 이어지는 통로와 포털 |
| 항구 도안 2 | 선착장·도심·시청·시장으로 연결되는 교차 통로 |
| 항구 도안 3 | 주점 진입부, 조선소, 항구 방향 통로 |
| 항구 도안 4 | 중앙 통로 양쪽 상인 구역과 우측 거래 대행인 |
| 주점 내부 도안 | 좌측 하단 출입구, 테이블 구역, 우측 카운터와 의자 |

영역별 별도 맵과 포털 연결을 사용한다. 예시 이미지에 추가된 길이나 장식 때문에 원래 도안의 연결 관계를 임의로 변경하지 않는다. 선착장 게시판은 함선 옆에 배치한다.

## 5. 시간·일과·취침

### 5.1 시간 규칙

- 게임 내 하루의 흐름은 현실 시간 10분이다.
- 대화·거래·항해 일지 등 관리 UI를 사용하는 동안 세계 시간이 멈춘다.
- 항해 중 이벤트가 허용한 배치 작업에서도 시뮬레이션을 정지한다.
- 전투 이벤트의 실제 전투 시뮬레이션은 진행되어야 한다. 대화 UI 정지와 전투 진행을 동일하게 취급하지 않는다.
- 메뉴를 중첩해 열고 닫았을 때 다른 정지 사유가 남아 있으면 시간이 재개되지 않아야 한다.

### 5.2 하루 흐름

기상 → 낚시·경비·대화·항해 계획·조타 등 자유 일과 → 침대 상호작용으로 취침 → 취침 중 이동 및 사건 판정 → 기상 또는 입항/이벤트로 취침 중단.

선원의 시간대별 업무 및 취침 시간은 자동으로 정한다. 플레이어는 주 업무를 설정하지만 시간표를 직접 편성하는 시스템은 이번 확정 범위에 없다.

### 5.3 취침 처리

- 취침을 이유로 무조건 다음 날 화면으로 즉시 전환하지 않는다.
- 배 위치를 취침 경과 시간에 해당하는 만큼 이동시킨다.
- 취침 중 사건이나 자동 입항이 발생하면 해당 시점까지만 이동한다.
- 자동 입항하면 취침을 중단한다.
- 사건 발생 시 그 사건에 맞는 대화·전투 이벤트로 진입한다. 이것이 ‘이벤트 씬’의 의미다.
- 대부분의 선원은 취침한다. 방향타를 맡은 일등 항해사와 같은 특별한 선원은 업무를 계속하며 식량도 소비한다.
- 취침 중에도 이동·계약·일지·이벤트 상태를 일관되게 갱신한다. 구현 방식이 시간 가속이든 계산 방식이든 사건 시점을 건너뛰지 않는다.

### 5.4 밤샘과 취침의 차이

| 상태 | 이점 | 영향 |
|---|---|---|
| 취침하지 않음 | 추가 낚시, 직접 방향타 확인, 세밀한 항로 조정 | 추가 부정적 이벤트 조건, 해적 접근 가능성 증가, 쥐·게 생성률 증가 |
| 취침 | 실제 플레이 시간 단축, 추가 이벤트 가능성 감소 | 자는 동안 이동하여 경로 이탈 가능, 쥐·게 신규 생성 없음 |

취침은 모든 사건을 무조건 제거하는 무적 상태가 아니다. 불침번 등 취침 중 발생 가능한 사건이 존재한다.

## 6. 항해·방향타·항해 일지

### 6.1 이동과 입항

- 배의 진행 방향은 1층 갑판의 방향타를 통해 조정한다.
- 함장실 지도에서 현재 배의 실시간 위치를 확인한다. 지도 확대·축소를 지원한다.
- 지도에 계획선을 그리는 행위만으로 배가 자동 이동하지 않는다.
- 해당 주특기·경력을 갖춘 일등 항해사가 있으면 계획 항로를 따라 자동으로 방향타를 조절한다.
- 바람은 속도·방향에 영향을 주지 않으며 별도 바람 시스템은 기획 범위에서 제외한다.
- 폭풍우 이벤트의 방향타 무작위 회전은 별도 사건 효과로 유지한다.
- 돛이 완전히 파손되어도 감속하여 계속 이동한다. 침몰은 없다.
- 항구의 입항 범위에 접근하면 자동 입항한다.
- 출항 후 일정 범위 밖으로 나가야 해당 항구의 재입항 판정이 다시 가능하다.

### 6.2 일지 접근과 기록

함장실의 일지와 상호작용해 열고 기록한다. 상단 중앙 HUD는 항해 일자 표시일 뿐, 어디에서든 일지를 여는 기능이 아니다.

| 기록 요소 | 규칙 |
|---|---|
| 실제 경로 | 일지 기록 시점까지의 해당 일자 미기록 경로를 누적 |
| 다중 기록 | 하루에 여러 번 기록 가능. 기존 기록에 이어 붙임 |
| 이벤트 아이콘 | 기록 가능한 이벤트의 실제 발생 위치에 표시 |
| 아이콘 편집 | 임의 아이콘 추가 불가. 기존 아이콘 제거·텍스트 메모 추가 가능 |
| 예상 경로 | 현재 항해 지도에 펜으로 작성·수정 가능 |
| 과거 기록 | 항구 간 항해 단위로 계획·실제 경로·이벤트·메모 보존 |
| 레이어 | 좌측 과거 항해 버튼을 토글하여 지도 위에 중첩 |

### 6.3 취침과 미기록 데이터

1. 이미 기록한 경로·이벤트는 보존한다.
2. 취침 전까지 발생했지만 기록하지 않은 이벤트는 취침 후 기록할 수 없다.
3. 일반적으로 기록하지 않은 경로는 기록에 공백으로 남는다.
4. 예외: 마지막 일지 기록 후 다른 이벤트나 상호작용을 하지 않고 취침했다면, 마지막 기록부터 취침까지의 이동 경로를 다음 기록에 반영한다. 취침 자체는 이 예외를 무효화하는 상호작용으로 취급하지 않는다.
5. 취침 상황에서 이동한 경로는 다음 날 경로로 반영한다.
6. 불침번 동안 이동한 경로도 다음 날 기록에 반영한다.
7. 이 예외가 취침 전 미기록 이벤트까지 복구하는 것은 아니다.

경로 기록용 임시 데이터와 확정 기록을 분리하고, 예외 적용 자격을 관리한다. 날짜 변경과 취침이 엇갈리는 경우의 내부 경계 처리는 위 규칙을 보존하여 구현 중 구체화한다.

## 7. 선원 능력·생활·업무

### 7.1 선원 정보

| 항목 | 의미 |
|---|---|
| 항해 경력 | 함선 승선 경력과 이력. 해적 경력은 미공개 정보로 존재 가능 |
| 이력 | 이전 함선 승선 이력 |
| 주특기 | 수행 자격 또는 업무 성능에 영향을 주는 전문성 |
| 체력 | 생존·전투·업무에 관여 |
| 힘 | 전투 및 관련 업무 성능 |
| 손재주 | 관련 업무 성능 |
| 지능 | 관련 업무 성능 |
| 희망 사항 | 존재할 수도 없을 수도 있는 근무·항로·시설 등의 조건 |
| 행복도 | 업무 성능과 작은 이벤트 가능성에 영향 |
| 신뢰도 | 업무 성능에는 직접 영향 없음. 낮으면 고위험 이벤트 가능성 증가 |

전투 성능은 체력·힘·항해 경력과 무기를 반영한다. 업무 성능은 체력과 업무에 해당하는 힘·손재주·지능, 항해 경력을 반영한다. 정확한 계산식과 계수는 구현·밸런싱 단계에서 정하며, 경력이 없다는 이유만으로 모든 행동 성능이 0이 되는 등의 결함은 방지한다.

행복도는 비교적 쉽게 변한다. 낮은 행복도가 지속되면 신뢰도가 서서히 감소한다. 신뢰도는 쉽게 변하지 않고 회복하기 어렵다. 항구에서는 선원 행복도가 회복된다.

### 7.2 생활 우선순위

식사와 취침은 일반적인 업무 수행보다 우선한다. 식량 부족 시 행복도와 체력이 감소하지만 식량 부족만으로 사망하지 않는다. 야간 특별 근무 선원은 지정된 예외에 따라 계속 근무할 수 있다. 체력의 능력치·현재 생명력 표현과 소비 주기는 구현 중 구체화한다.

### 7.3 업무 배정과 자동 탐색

- 플레이어가 선원과 상호작용하여 주 업무를 설정한다.
- 일회성 클릭 명령이 아니라 시간대에 맞춰 지속 수행할 담당 업무다.
- 주 업무가 없거나 수행할 수 없으면 남은 업무를 탐색한다.
- 특별 업무는 해당 주특기가 없으면 담당할 수 없다.
- 일반 업무는 누구나 자동 탐색하여 수행할 수 있다.
- 동일 업무에 여러 선원이 접근하면 먼저 맡아 진행한 선원이 우선한다.
- 선원은 전체 업무를 탐색해도 수행할 남은 업무가 없으면 휴식한다.
- 사망·수감·취침·전투 등으로 업무를 중단하면 점유가 영구히 남지 않도록 처리한다.

### 7.4 채택된 초기 주특기

| 주특기 | 업무 등급 | 적용 |
|---|---|---|
| 항해 | 특별 | 일등 항해사로서 계획 항로 조타, 취침 중 근무 |
| 정비 | 특별 | 수리도구를 소비해 기능 타일 수리 |
| 경계 | 일반 | 망루 탐지 업무의 성능 증가 |
| 경비 | 일반 | 선내 유해 생물 제거 업무 성능 증가 |
| 낚시 | 일반 | 낚시 시스템 구현 후 업무 성능 증가 |

직급과 주특기를 동일한 값으로 강제하지 않는다. 게시판의 직급 표시와 특별 업무 자격을 각각 표현할 수 있어야 한다. 구체적인 직급 종류와 경력 조건은 구현 중 정한다.

## 8. 고용·계약·게시판·후불 정산

### 8.1 고용 과정

주점에서 선원 소개 → 능력·외형·이력 확인 → 협상 및 평가 → N회 항해 계약·선불/후불 선택 → 계약 생성.

- 스탯을 기반으로 1회 항해당 기본 고용 금액을 계산한다.
- 가격 협상으로 기본 금액이 변할 수 있다.
- 평가 슬라이더는 저평가~고평가이며 고용 금액 조정 범위의 원문 기준은 -50~+50이다. 단위와 구체 계산은 구현 중 결정할 밸런스 항목이다.
- 평가에 따른 행복도·신뢰도 변화가 UI에 즉시 표시된다. 미확정 미리보기와 실제 고용 확정을 구분한다.
- 조정된 1회 금액 × N회가 총 계약 금액이다.
- 예시 UI의 ‘최종 금액’은 1회 기준, ‘최종 비용’은 전체 계약 금액으로 구분한다.

### 8.2 협상과 약속

무작위 대화 패턴을 사용한다. 선원은 희망 업무, 다음 목적지, 선내 시설과 옵션을 제안할 수 있다. 최근 항해 소문과 플레이어 명성도 흥정에 영향을 준다. 약속을 지키지 않으면 해당 선원의 신뢰도가 지속적으로 감소한다. 구체 대화 문장·가격 계수·판정 주기는 데이터로 확장한다.

### 8.3 지급 규칙

| 조건 | 지급 시점·결과 |
|---|---|
| 선불 | 계약 시 N회분 전액을 한 번에 지급 |
| 후불 | N회 항해가 모두 끝난 후 전액을 한 번에 지급 |
| 계약 잔여 횟수 있음 | 입항해도 생존 선원은 계약 유지 |
| 계약 만료 | 해당 항구 게시판에서 재고용 시도 가능 |
| 용서 | 기존 계약과 선불·후불 조건 유지 |
| 생포·처형·사망 | 계약 파기. 선불 반환 없음, 후불 지급 불필요 |

‘반란 선원 급여 면제’라는 독립 규칙은 사용하지 않는다. 정산 여부는 계약 유지·파기 상태로 판단한다. 별도의 월별 급여를 이 계약 금액에 중복 부과하지 않는다.

### 8.4 선착장 게시판

함선 옆 게시판과 상호작용하면 UI를 연다. 두 영역을 명확하게 구분한다.

| 영역 | 표시 대상 |
|---|---|
| 현재 고용 내용 | 잔여 항해가 있는 선원, 현재 항구에서 새로 고용한 선원 등 현재 계약 상태의 선원 |
| 과거 고용 내용 | 직전 항해를 함께했고 이번 항구에서 재고용 가능한 선원. 다른 항구에서 계약이 종료된 선원은 제외 |

표시 정보: 이름, 직급, 선불/후불, 계약 금액, 남은 계약 횟수. 지급·재계약 처리를 위해 계약 상태와 미정산 금액도 명확히 표시한다. 선원별 후불 지급과 재계약 진입을 지원한다.

계약 횟수가 남은 선원을 입항 때마다 강제로 해고하지 않는다. 다른 항구에서 끝난 과거 계약을 전 세계 공통 재고용 목록으로 남기지 않는다. 만료·미정산 계약을 숨겨 지급할 수 없게 하지 않는다. 명단 배치의 세부 UX는 이 범위를 지켜 구현 중 정한다.

반란 이력이 있는 일부 선원은 재계약이 제한될 수 있다는 원문 조건을 유지하되, 해당 대상의 세부 선정 기준은 후속 콘텐츠 규칙으로 둔다. 용서한 선원의 현재 계약은 유지된다.

### 8.5 미정산 상태에서 출항 시도

1. 지불 기한이 된 후불금이 있는지 검사한다.
2. 미정산 상태라면 강제 매각 UI를 활성화한다.
3. 사용자가 매각할 무역품을 선택한다. 필요한 금액을 초과하여 매각할 수 있다.
4. 강제 매각 가격은 항구 시장가의 60%를 초기 임시값으로 사용한다.
5. 확보한 금액으로 정산한다. 매각액 중 정산에 사용하지 않은 잔액을 중복 차감하거나 소멸시키지 않는다.
6. 그래도 남은 미지급금에 비례하여 명성을 감소시킨다.
7. 미지급금은 소멸하며 다음 항해로 이월하지 않는다.
8. 감소 후 명성이 게임 오버 기준값 이하이면 게임 오버, 초과이면 출항을 진행한다. 다른 출항 금지 조건은 별도 적용한다.

명성 감소 비율과 게임 오버 기준값은 임시 설정이다. 지급 실패 자체만으로 즉시 게임 오버로 처리하지 않는다.

## 9. 함선 타일·시설·물자

### 9.1 배치와 해금

- 항해 중에는 해금된 타일만 활성화·시각화한다.
- 잠금 타일은 이동하거나 통과할 수 없다.
- 항구 조선소에서 개조·타일 추가·잠금 해제를 수행한다.
- 항해 중에는 특정 이벤트가 허용할 때만 배치하고 배치 과정에서는 시뮬레이션을 정지한다.
- 시설은 층 제한, 점유 크기, 고정 여부, 기능 상태, 내구도를 가진다.
- 화장실·망루 등 일부 시설은 함선별로 정해진 고정 위치를 가질 수 있다.

### 9.2 시설

| 시설 | 원문 크기 예시 | 기능·제약 |
|---|---|---|
| 침대 | 2×1 | 필수. 선원 수 이상 필요. 1층 갑판 배치 불가 |
| 대포 | 1×2 | 전투 진입 전 적 체력을 타일 수에 비례해 감소. 특정 층 배치 불가 |
| 화물 적재 | 1×1 | 필수. 타일 수에 비례해 적재 가능량 증가 |
| 선내 감옥 | 1×1 | 유닛 수감. 공간이 있어야 생포 선택 가능 |
| 화장실 | 예시 미지정 | 행복도에 영향 |
| 무기고 | 예시 미지정 | 무기 보관·무장 설정·전투 준비 |
| 망루 | 예시 미지정 | 탐지 자동화 |
| 방향타 | 예시 미지정 | 현재 진행 방향 조절 |
| 항해 일지 | 예시 미지정 | 함장실에서 지도·기록 접근 |

시설 분류상 타일 또는 추가 파츠로 표현되는 구체 방식은 함선 데이터에 맞춰 구현한다. 낚시터·추가 돛 등 부품도 추가·업그레이드 대상으로 지원한다.

### 9.3 출항 제한

출항을 금지하는 시설 조건은 다음 두 가지다.

- 침대 수가 선원 수보다 적다.
- 필수 타일의 기능이 정지해 있다.

필수 시설은 최소 1개 이상 배치되어야 하는 함선 구성 규칙을 유지한다. 필수 시설 누락을 ‘정상 작동’으로 판정하지 않는다. 식량 부족을 별도의 출항 금지 조건으로 추가하지 않는다. 선원 0명인 상태도 출항 가능하다. 후불 정산·게임 오버 처리는 별도 절차다.

### 9.4 내구도와 수리

쥐·게·따개비 등은 기능 타일에 접근해 지속 피해를 준다. 내구도가 감소하면 점선 윤곽이 검은색에서 붉은색으로 변하고 타일 색이 어두워진다. 내구도 소진 시 기능이 정지한다.

| 상태 | 수리 방법 |
|---|---|
| 완전 파손 전 | 정비 선원이 수리도구를 소비해 지속 수리, 또는 조선소 수리 |
| 완전 파손 | 조선소에서 수리해야 함 |
| 조선소 수리 | 최대 내구도로 회복. 개별·일괄 수리 지원 |

침몰은 없다. 돛 완전 파손은 이동 불가 대신 감속으로 처리한다.

## 10. 전투·패배·반란·포로

### 10.1 전투 진행

- 전투 이벤트가 시작되면 선원은 자동으로 무기고를 경유해 전투에 참여한다.
- 무기고가 없으면 바로 전투에 참여한다.
- 전투 예측 후 시작 전이라면 개인·일괄 사전 무장 명령이 가능하다.
- 무기고 상호작용으로 선원별 무기·무장 여부를 설정하고 현재 상태를 시각화한다.
- 플레이어 캐릭터는 전투에 참여하지 않는다. 시작 후 전투 명령으로 개입할 수 없다.
- 전투 엔티티는 체력바와 공격 쿨타임 바를 가진다.
- 칼은 빠른 공격 속도와 범위 공격, 총은 느린 공격 속도와 투사체 공격을 사용한다.
- 아군 오사·팀 공격은 적용하지 않는다.
- 선원은 전투 중 사망할 수 있다.
- 대포 타일 수에 따른 적 체력 선감소를 전투 진입 전 적용한다. 예시 이미지의 반복 포격 스킬은 추가 확정 사양이 아니다.

무기고 경유 동선, 사전 무장 선원의 확인 동작, 무기 재고 부족 시 처리 등은 교착을 막는 방향으로 구현 중 구체화한다. 사용자가 사전 무장을 지시한 결과를 전투 시작 시 임의로 해제하지 않는다.

### 10.2 패배 규칙

해적·크라켄·반란은 결과 처리 구조를 공유한다.

| 상황 | 결과 |
|---|---|
| 선원 없이 전투 발생 | 자동 패배 |
| 전투 중 아군 선원 전원 사망 | 패배. 플레이어는 생존 |
| 패배 시 무역품 보유 | 무역품의 10~70% 약탈 |
| 패배 시 무역품 없음 | 보유 골드의 30~70% 약탈 |

몰수 대상 재산은 무역품이다. 다른 보유 함선·시설·장비를 임의로 약탈 대상에 추가하지 않는다. 무역품이 있는 경우 무역품 약탈 후 남은 골드까지 자동으로 중복 약탈하지 않는다. 품목별 배분과 정수 수량 반올림은 구현 중 결정한다. 공유 결과 구조를 쓰더라도 사건별 설명·연출은 맞게 표현한다.

### 10.3 반란과 승리 후 처분

- 선원의 과반수가 신뢰도 10% 이하인 경우 반란이 발생한다.
- 신뢰도가 낮은 선원과 전투한다.
- 진압 후 처리 가능한 대상에 대해 처분 UI를 제공한다.
- 감옥에 공간이 있으면 생포를 선택할 수 있다.
- 공간이 없다면 처형 또는 용서한다.
- 생포·처형·사망은 계약 파기, 선불 반환 없음, 후불 지급 불필요다.
- 용서는 계약 유지이며 보상금을 얻을 수 없다.
- 이미 사망한 유닛을 생포 대상으로 되살리지 않는다. 진압 후 처분 대상 판정의 세부 전투 규칙은 구현 단계에서 구체화한다.

### 10.4 포로

생포한 선원은 감옥 공간과 식량을 소비한다. 시청 상호작용으로 인계하고 보상금을 받는 시스템을 구현한다. 인계하지 않으면 다음 항해에도 감금이 유지된다. 인계 보상과 처분·계약 종료는 한 번만 적용해야 한다.

## 11. 이벤트·상호작용·미니게임

### 11.1 초기 구현 이벤트

| 이벤트 | 주요 규칙 | 연결 시스템 |
|---|---|---|
| 쥐 발생 | 시설 접근·피해, 선원 제거 | 업무·내구도·생활 |
| 폭풍우 | 갑판 선원 체력 감소, 펼친 돛 지속 피해, 방향타 무작위 회전 | 항해·시설·이벤트 |
| 해적 습격 | 자동 무장, 관전 전투, 사망·약탈 | 전투·계약·재고 |
| 불침번 | 취침 중 기상, 일정 시간 순찰, 침대 선택 시 종료, 미충족 시 다른 사건 가능성 증가 | 취침·시간·일지 |
| 무인도 발견 | 대화 선택으로 선원 파견·보상·후속 결과 | 대화·선원·이벤트 |
| 선상 반란 | 신뢰도 조건, 전투, 생포·처형·용서 | 신뢰도·전투·감옥·계약 |

후속 확장 이벤트: 크라켄, 물고기떼, 게, 따개비. 물고기떼는 특정 지역에서 무작위로 발생해 선내에 물고기가 떨어지고 식량을 얻는 사건이다.

### 11.2 장비 상호작용

- 망원경: 인근 해적선·섬 등과 사건을 예측한다. 없으면 빈 바다를 보여 준다. 환경에 따라 정확도가 낮아질 수 있다.
- 망루: 탐지를 자동화한다.
- 무기고: 선원별 장비·무장, 일괄 무장·해제.
- 방향타: 진행 방향 수정.
- 항해 일지: 함장실에서 기록·계획·과거 항해 레이어 확인.
- 침대: 취침 또는 불침번 종료.

### 11.3 낚시와 보드게임

필수 프레임워크를 먼저 완성하고, 미니게임은 이후 설계·구현한다.

낚시의 확정 연결 규칙:

- 플레이어 직접 낚시는 미니게임이다.
- 선원 낚시는 미니게임 없이 업무 성능으로 진행한다.
- 잡은 물고기는 하루 소모 식량을 대체할 수 있다.
- 항구에서 함선에서 내릴 때 남은 물고기는 재고로 전환된다.

보드게임의 확정 연결 규칙:

- 쉬고 있는 선원과 플레이한다.
- 골드 획득 또는 손실이 발생할 수 있다.
- 전원 근무 중이면 참여자가 없으므로 플레이할 수 없다.

구체 게임 종류·입력·승패·보상 곡선은 후속 단계에서 설계한다. 해당 단계 이전의 연결 지점 준비를 미니게임 완성으로 보고하지 않는다.

## 12. 항구·무역·상품·명성

### 12.1 주점

- 무역·환경·이벤트 정보를 제공한다.
- 지불 금액에 따라 정보 등급이 달라진다. 원문의 1~10G는 예시이며 항구마다 범위가 다르다.
- 선원을 소개하는 고용 창구다.
- 소개비를 지불하면 금액에 따라 품질이 다른 선원을 추천한다.
- 항구별 평균 선원 등급이 다르다.

### 12.2 시장

상인은 품목별로 구분되며 플레이어는 상인에게 구매한다. 재고 판매는 거래 대행인에게 한다. 상인별 취급 품목을 구분하고 예시 화면처럼 모든 물건을 한 상인이 판매한다고 자동 해석하지 않는다.

상인 종류: 식품, 채소, 고기, 생선, 의류, 무기, 의약품, 향신료, 세공품. 식품 상인은 항해 중 먹을 수 있는 육포류를 취급한다. 항구 평판은 거래 가격에 영향을 준다.

### 12.3 초기 상품 구성

| 구분 | 품목 | 기능 |
|---|---|---|
| 항해 식량 | 육포 | 선원 식량 소비 |
| 일반 무역품 | 채소·육류·생선·직물·향신료·세공품 | 항구 거래·주민 요청 |
| 수리 물자 | 수리도구 | 정비 시 소비 |
| 무기 | 칼·총 | 무기고 보관·장비 설정 |
| 후속 기능 | 의약품 | 치료 규칙 확정 후 사용 기능 추가 |

상품은 거래 가능 여부, 항해 중 소비 용도, 무역품 약탈 대상 여부를 구분한다. 일반 무역품이 음식처럼 보여도 자동으로 식량으로 소비한다고 가정하지 않는다. 낚시 물고기의 식량 대체·재고 전환 규칙은 별도로 유지한다.

### 12.4 수요와 상태 갱신

항구·나라별 수요 차이에는 날씨, 계절, 전쟁·가뭄·역병 등의 특수 상황, 유행, 플레이어의 현지 호감도·인기도가 영향을 준다. 날씨에 따른 수요 변화는 배를 움직이는 바람 시스템과 별개다.

채택한 초기 갱신안은 게임 내 날짜 변경 시 항구 가격·수요·재고를 갱신하는 방식이다. 정확한 가격 산식·변동폭·공급량과 상황별 효과는 구현 중 구체화한다. UI를 열어 시간이 멈추면 날짜도 진행하지 않는다.

### 12.5 주민 거래 요청

- 거래 대행인 UI 우측 1/3에 표시한다.
- 주민이 특정 상품 또는 골드를 요구하고 골드 또는 물품을 보상한다.
- 플레이어가 이득 또는 손해를 볼 수 있다.
- 요청은 위에서 아래로 쌓이고 동시에 존재하는 최대 개수가 있다.
- 각 요청은 제한 시간이 지나면 소멸한다.
- 시간은 게임 시간에 연결하며 대화·거래 UI의 시간 정지 동안 함께 멈춘다.
- 원문의 ‘30~3분’은 단위가 확정되지 않은 예시다. 확정 수치로 복사하지 않고 구현 중 임시 만료 시간을 정한다.

### 12.6 시청

퀘스트를 수주한다. 성공 시 평판 증가와 보수를 지급하고, 실패 시 평판을 감소시킨다. 생포 선원 인계와 보상금 지급도 시청 상호작용으로 지원한다. 퀘스트 세부 목록·목표·기간은 후속 콘텐츠 데이터로 확장한다.

### 12.7 조선소

- 기능 타일 개별·일괄 수리.
- 기능 타일 업그레이드·재배치·제거·구매·해금.
- 함선 구매·판매·교체.
- 보유 중인 다른 함선으로의 교체는 해당 함선이 있는 항구에서만 가능.
- 함선별 고정 타일과 층 제한 적용.
- 망루·낚시터·추가 돛 등의 파츠 추가·업그레이드.
- 함선 변경 시 선원·화물·포로의 수용 가능 여부와 이전 처리를 검사한다. 상세 UI는 구현 중 구체화한다.

### 12.8 명성·평판

전역 명성은 고용 협상과 미지급금 처리 및 게임 오버에 연결한다. 항구의 현지 평판·호감도·인기도는 가격·수요·퀘스트 등에 연결한다. 이 값들을 이유 없이 하나로 합쳐 어느 항구의 실패가 곧바로 전역 게임 오버가 되게 하지 않는다. 통합 여부와 세부 식은 확정 역할을 보존하여 구현 중 구체화한다.

## 13. 저장·종료·게임 오버

### 13.1 저장 정책

- 저장 파일로 이어하기를 지원한다.
- 게임 종료 시 저장한 뒤 종료한다. 사용자가 말한 수동 저장은 이 동작을 뜻한다.
- 이벤트 발생·종료 등의 주요 상황에서 자동 저장한다.
- 별도 과거 저장 슬롯을 선택해 되돌리는 기능은 제공하지 않는다.
- 마지막 저장 이후 진행을 재실행으로 되돌리는 것은 허용한다.
- 정상 종료는 저장 후 종료하므로, 저장 이후 변경을 의도적으로 버리는 별도 종료 기능을 기본으로 만들지 않는다.
- 게임 오버가 확정된 해당 플레이는 과거 수동·자동 저장을 포함하여 게임 내에서 이어할 수 없다.

### 13.2 저장 대상

현재 날짜·시간, 월드와 항구 상태, 배 위치·방향·입항 재활성 상태, 함선 소유·정박 위치·타일·내구도, 재고·골드·명성, 선원 능력·생존·계약·업무·무장·생활 상태, 포로, 퀘스트, 이벤트 진행·결과 반영 여부, 항해 일지·미기록 경로·취침 이월 자격, 현재 플레이 종료 상태를 보존한다.

### 13.3 구현 안전성

저장은 중간 파일 손상으로 진행이 사라지지 않도록 원자적으로 처리하고 버전을 관리한다. 거래·약탈·계약 횟수 차감·포로 보상·명성 감소 같은 결과는 불러오기 후 중복 적용되지 않아야 한다. 게임 오버 상태는 해당 플레이의 복원 가능 상태보다 우선한다. 외부 파일 변조 방지나 온라인 검증은 확정 요구에 포함하지 않는다.

## 14. 안정적인 기반 구조

이 절은 기능 우선순위보다 기반의 안정성을 우선하라는 사용자 요구를 구현하기 위한 기준이다. 구체 클래스명·패키지·Unity 버전은 구현 환경에서 결정한다.

| 기반 | 책임 |
|---|---|
| 게임 진행 상태 | 항구·항해·취침·대화·전투·편집·게임 오버의 전환 |

| 입력 계층 | PC 행동과 모바일 입력을 같은 게임 행동으로 연결 |
| 상호작용 계층 | 대상 탐지, 실행 가능 여부, UI 진입, 상태 전환 |
| 데이터 정의 | 함선·시설·상품·선원 특기·이벤트·퀘스트·밸런스 설정 |
| 런타임 상태 | 정의 데이터와 분리된 현재 내구도·재고·계약·위치 |
| 업무 시스템 | 자격 검사·탐색·선점·수행·중단·해제 |
| 항해 시스템 | 위치·방향·속도·입항·계획 경로·일등 항해사 |
| 이벤트 시스템 | 조건·발생·분기·종료·결과·저장 경계 |
| 경제·계약 | 재고 이전·골드·계약 생성·횟수·미지급금·명성 |

- 층이나 항구 화면을 바꿔도 핵심 진행 상태가 초기화되지 않는다.
- 보이지 않는 층의 선원이 정지하지 않는다.
- 전투·계약·재고·저장이 동일 인물과 물품을 안정적인 식별자로 참조한다.
- 대화·거래 등의 정지는 한 곳에서 관리한다.
- 서로 다른 입력 장치가 동일한 행동을 실행하도록 분리한다.
- 밸런스 값과 콘텐츠 목록은 교체 가능한 데이터로 둔다.
- 세계 생성은 이후 교체할 수 있도록 구성하되, 초기부터 무작위 생성 전체를 만들 필요는 없다.
- 구현 초기부터 상태 확인 수단을 마련해 시간·업무·계약·이벤트 결과를 검증한다.
- 임시 자산은 대체 가능하게 연결하고, 최종 완료 전 지정 그래픽 기준으로 교체한다.

각 단계는 직전 단계의 작동을 유지하면서 확장한다. 화면만 만든 상태를 기능 완성으로 보고하지 않는다.

## 17. 구현 중 구체화할 항목

다음은 누락으로 간주해 기획을 다시 중단할 항목이 아니라, 사용자가 구현 단계에 위임한 범위다.

- Unity 버전·패키지, 세부 데이터 구조, 경로 탐색·업무 탐색 방식.
- PC 키 배치, 상호작용 거리, 카메라 세부 동작, 해상도별 UI 대응.
- 시작 자금·명성·함선 상세 배치·항구 수·상품 수량·선원 후보 수.
- 능력 산식, 가격·수요·재고 계산, 이벤트 확률, 이동·공격·수리 속도.
- 강제 매각 비율의 최종 밸런스, 미지급금-명성 환산, 게임 오버 기준.
- 특별 업무 경력 조건, 직급 세부 목록, 업무 후보 정렬·선점 해제 세부 정책.
- 시설 재배치·함선 교체 시 적재·수용량 변경 UX.
- 반란 진압 후 처분 대상 판정, 재계약 제한 세부 기준.
- 약탈 품목별 배분·정수 처리, 선택지별 보상·파견 위험.
- 정보 대사·퀘스트·상인 품목 확장과 콘텐츠 수량.
- 낚시·보드게임의 구체 규칙과 입력, 치료 시스템.
- 세부 효과음·음악·애니메이션·층 전환 일러스트.
- 모바일 실제 입력은 PC 완성 후, 세계 커스텀·무작위 생성은 향후 확장.

이미 확정된 계약 지급 시점, 게임 오버 조건 구조, 저장 정책, 관전 전투, 일지 기록 규칙, 그래픽 기준을 이 목록을 근거로 재설계하지 않는다.

## 19. Codex 전달 지침

이 문서와 함께 제공된 참고 자료를 읽고, 15절의 기반 단계부터 구현한다. 각 단계 시작 시 해당 요구와 완료 기준을 연결하고, 종료 시 실제 구현된 기능·검증 결과·남은 후속 기능을 구분해 보고한다.

구현 과정에서 다음 기준을 지킨다.

1. 1절의 자료 역할과 18절의 변경 사항을 먼저 확인한다.
2. 화면 구성은 대응 도안을 직접 확인하고, 그래픽 방향은 최종 레퍼런스로 판단한다.
3. 기존 규칙을 지키는 구현 세부사항은 자율적으로 결정하고 기록한다.
4. 사용자 지정 수치를 초기 기준으로 사용하고 나머지 값은 조정 가능한 임시값으로 만든다.
5. 한 단계의 핵심 상태와 저장 복원을 확인한 뒤 다음 단계로 확장한다.
6. 최종 규칙이나 구도를 바꾸는 선택만 사용자에게 확인한다.
7. 원문·이미지의 미승인 기능을 임의 추가하지 않는다.
8. 최종 완성은 PC 전체 흐름과 그래픽 검수 후 모바일 입력까지 단계별로 판단한다.

이 문서의 확정 범위는 이후 구현을 진행하기에 충분하다. 17절의 세부사항을 모두 사전 확정하기 위한 추가 기획 절차를 요구하지 않는다.

## 부록 B. 초기 노트 대조와 구현 시 주의점

<a id="original-note"></a>

`Original_Idea.txt`는 초기 구상에 대한 근거다. 최종 본문 18절의 변경 사항을 우선하며, 아래 대조는 초기 규칙이 개발 중 되살아나는 것을 막기 위한 것이다. README의 구현 시작 안내도 이번 작업의 실행 명령으로 취급하지 않았다.

- **계약 지급:** 선불은 고용 시 계약 전체 금액, 후불은 N회 계약 종료 시 전체 금액이다. 항해마다 분할 지급하거나 월급·보너스·반란 임금 면제 규칙을 임의로 붙이지 않는다. 사망·처분·용서·계약 잔여 여부의 예외까지 8절을 함께 적용한다.

## 2026-10-19 선원 이동·작업·휴식 보완
